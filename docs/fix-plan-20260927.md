## 附三：推理端到端耗时优化（2026-09-28，提交 5d02586）

**耗时解剖**（GPU 热态同任务三连测）：管线本身仅 1.7-1.9s（kml 冷缓存 6.6s→热 0.2s；推理核心 1.3s），但端到端 34-36s——**97% 耗时在管线之外**。按 started_at 三分：排队（create→claim）14-29s + 执行 4-5s + 发布 1s。排队时长全部 ≤30s 且与 30s 心跳时刻精确吻合。

**根因**：MySQL REPEATABLE READ 下 worker 会话的读事务不结束，新插入的 `queued` 行对旧快照不可见；`claim_next_job` 空转分支直接 return（无 commit/rollback），下一次 SELECT 仍在同一快照——任务只能等 30s 心跳的 commit 刷新快照后才被「看见」。`refresh_job` 同病：取消标记最多延迟一个心跳周期才可见。

**修复**（backend/applications/inference/jobs.py）：`claim_next_job` 空转分支增加 `db.session.rollback()`；`refresh_job` 先 rollback 再 refresh。写路径全部即时 commit，无吞写风险。

**实测对比**（同数据集同年份，GPU 热态）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 排队 create→claim | 14-29s（心跳抖动） | **0-1s** |
| 执行 claim→终态 | 4-5s | 5s |
| 端到端（DB） | 34-36s | **5-6s** |
| 客户端观测（含 1s 轮询粒度） | ~35s | **8-9s** |

回归：test_inference_jobs.py 新增快照释放契约 2 例；后端全量 **1332 passed / 36 skipped**。

运维事实：worker 重启后首个任务仍会撞上模型初始化（1.97GB 加载约 40-60s），属启动成本非排队问题；稳态下「提交→出结果」个位数秒。
