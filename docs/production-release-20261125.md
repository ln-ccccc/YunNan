## 8. 发现的问题与限制

### 8.1 切换期间推理 worker 崩溃重启 3 次

**经过**：第一阶段重建了后端和两个 worker，三者都在一分钟内健康；脚本随即开始构建 GeoView（占 1–2 GB 内存）。
推理 worker 启动时会把模型加载到 GPU，加载过程要在宿主内存里临时展开 1.84 GB 的权重。两者重叠时虚拟机内存不够
（日志：`OSError: [Errno 12] Cannot allocate memory`，随后"宿主可用内存 2.07 GiB 低于 CPU 模型加载所需约 4.04 GiB"），
worker 进程退出，被重启策略拉起；第二次重试同样失败；GeoView 与 Miner 构建结束、内存释放后，第三次（15:53:12）成功，
显存回到 6.5 GB，15:54 起保持健康。

**这不是候选版本引入的**：worker 启动即加载模型的行为、代码、镜像与切换前完全相同。它是"先重启推理 worker、紧接着构建 GeoView"
这个切换顺序在 6 GB 内存的虚拟机上的资源冲突。演练栈不带推理 worker，所以此前没暴露。

**对现在的生产**：没有影响。之后真实 GPU 推理、15 分钟观察都正常。

**对以后的影响**：任何一次"推理 worker 重启"与"前端构建或其它吃内存的操作"重叠，都会重现这个崩溃重启，直到内存释放后自愈。
回滚也会走同样的顺序，所以**回滚时预计同样会重启几次，属于已知现象，等它稳定即可**（脚本第一阶段只等健康检查，
健康检查在模型加载完成之前就会通过，所以不会卡住切换）。

**建议的后续修复（这次没有改，按"不在生产现场改代码"的约定留待单独做）**：切换脚本在重启推理 worker 之后，
等模型加载完成（例如等显存占用回到加载后的水平）再开始下一阶段；或者把 GeoView、Miner 的构建排在推理 worker 之前。

### 8.2 经宿主端口访问时，"不读请求体就拒绝"的请求会让客户端一直等

接口冒烟里有一条"真的发送超过 10 MiB 的请求体"：经 `127.0.0.1:5008` 访问时客户端等不到响应。隔离的结果：

| 路径 | 未读请求体（5 MiB 与 11 MiB） |
| --- | --- |
| 宿主 → 发布端口 5008 | 客户端一直等（未登录的请求也一样） |
| 容器网络内直连 `backend:5008` | 3–22 毫秒返回（401 / 422「请求 JSON 超过 10 MiB」） |

所以后端应用本身的行为是对的，挂起出在 Docker 端口转发这一段：服务端不读请求体时，转发层不把响应送回客户端。
上线前就存在（未登录的大请求体同样如此），不是这次发布引入的；演练栈的端口只绑在本机回环地址上，走的是另一条路径，所以没复现。

**影响**：生产成果的几何 JSON 最大 0.72 MiB（3,044 条成果含历史修订），离 10 MiB 的上限有十几倍，正常的保存与几何请求碰不到。
会碰到的只有异常客户端，后果是它自己等到超时。

### 8.3 Miner 与 GeoView 要用同一个主机名访问

Miner 的配置把 GeoView 指向 `localhost:3000`。登录会话的 cookie 按主机名区分：用 `127.0.0.1:4000` 打开 Miner、
再点"编辑矢量"，弹出的是 GeoView 自己的登录页；用 `localhost:4000` 打开则直接进入编辑器。这是既有配置行为，不是缺陷，
验收脚本最初用错了主机名。
