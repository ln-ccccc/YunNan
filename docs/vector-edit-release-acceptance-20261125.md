## 2. 任务一：简化精度

细节都在 [对照实验报告](geometry-engine-adaptive-tolerance-20261125.md)。这里只留结论和本轮的实证。

**方案**：自适应容差加精度门槛。初始容差 `min(1 × 像元, 0.05 × √最小部件面积, 1 米)`，GEOS 拓扑保持简化，
结果必须通过保存同款校验、结构不变、逐部件面积变化 ≤ 3% 且对称差 ≤ 5%；不过关就把容差减半重试（四级），
仍不过关就拒绝、原面保持不变。

**为什么是它**：固定 1e-5 度会改动 95% 的图斑，面积变化中位数 13.3%、最大 159%。只用"像元的固定倍数"也不行——
1 个像元时小图斑的面积变化中位数 2.4%、95 分位 12%、最大 60%。全量数据上两种方案的对照：

| 指标 | 现行（固定 1e-5 度） | 新方案 |
| --- | --- | --- |
| 有变化 / 原样 / 拒绝 | 95.05% / — / — | 69.2% / 23.3% / 7.5% |
| 顶点压缩（有变化的） | 82.8% | 56.6% |
| 面积相对变化 P50 / P95 / 最大 | 13.3% / 34.0% / 159% | 0.26% / 1.73% / 3.00% |
| 贴边长度保持 | 18.4% | 64.75% |
| 图斑间新增重叠 | +193,593 m² | +62,336 m² |
| 被覆盖面积的净变化 | −1.064% | −0.223% |

**本轮补做的核对**：

- **137,040 与 137,042 的差异**。重新数了上一轮保存的原始输出：同一份数据、同一套简化代码，三次计算的"有变化"个数
  分别是 137,040（定稿回归，绑定 `f232238`）、137,041（叠加验证，它独立重算了一遍）、137,042（绑定 `36103e84` 的运行）。
  差 1–2 个，来自上一轮记录的 GEOS 3.10.3 拓扑保持简化的不确定性。上一轮报告把两次计算的数拼在了一行里
  （"119,254 个为 0；17,788 个不为 0"），与两次的总数都对不上，已按原始输出订正为 119,253，并写明来源。
- **新方案在同一批数据上各只算一次**，上表的对照数就是按这个口径补的（图斑间重叠、被覆盖面积）。
- **确定性**：新方案连算两次 0 / 144,176 不同；上一轮查出的 8 个不稳定图斑各连算 100 次，每个都只有 1 种输出。

**真实服务上的印证**（隔离演练）：EPSG:3857 下名义 0.5 米的像元，后端报出的地面尺寸是 0.4501 米——按真实尺寸算，
没有照搬名义值。EPSG:4326、名义 0.3 米的像元报 0.3006。

## 3. 任务二：前端的异步校验

**问题**：上一轮的编辑期校验在请求失败时是静默的——断网、超时、后端 404 / 500、响应格式异常，界面上什么都不显示，
不合法的面和"已确认合法"看起来一样。撤销 / 重做、合并、简化失败时的状态也没有同步。

**做法**：状态与提示逻辑抽成纯逻辑模块（`utils/classificationEditorValidation.mjs`），组件只做接线。

- 每个面处在 **校验中 / 合法 / 不合法 / 未确认** 之一。"未确认"不代表合法也不代表非法，可以继续编辑，保存始终由后端裁定。
- 一条结论是否过期（**Stale**）逐面判定：送审时记下几何指纹，结论回来时与画布现状逐值比较，对不上就丢弃；
  同一批里没被改过的面结论照常有效。
- 工具区新增一句校验状态（校验中 N 个面 / N 个面未通过校验 / N 个面未确认）。
- 撤销 / 重做、保存、合并、简化、删除之后同步逐面状态。
- 合并 / 简化的响应先过形状检查，对不上整次按失败处理；改动画布只经一个入口，抛错就恢复成改动前的画布。
- 不重复提交未改动的简化结果（后端接口不保证幂等，全量数据上第 2 次简化仍有 5.1% 的面会变）。

**测试**：

| 3 | ROI 掩膜精度 | 自动矢量化先把 ROI 栅格化到 label 的像元网格再裁切，边界精度受像元尺寸限制（0.02–1.89 米）；贴边图斑因此带着阶梯形的边界 | 贴边图斑多出大量顶点，也是它们难以简化的根源 | 用矢量的 ROI 裁切（`intersection`）替代像元掩膜，或至少叠加一次矢量裁切 |
| 4 | 小于 16 像素的连通域被丢弃 | `MINIMUM_COMPONENT_PIXELS = 16`：自动矢量化丢掉小于 16 个像元的连通域。阈值是像元数，对应的实际面积随像元尺寸相差一万倍（0.006 m² 到 57 m²） | 细像元成果丢失小图斑；粗像元成果保留了相对很大的碎块 | 改成按面积或按地类设阈值，并在成果上记录丢弃了多少、多大 |
| 5 | 变化矩阵要素顺序 | 您点名的既有项。本轮只核实到：变化矩阵取最近两期（`classification_stats.py` 的 `years_sorted[-2]`、`[-1]`），转移矩阵按行 = 旧类别、列 = 新类别写出。**涉及矢量要素进入矩阵的顺序规则，本轮没有展开核实** | 顺序不一致时同一对成果两次计算可能得到不同的矩阵 | 单独核实后补证据 |
| 6 | 历史图斑重叠 | 自动矢量化之后图斑之间本来就有重叠（全量合计 9,026 m²）；编辑与简化会让相邻图斑的公共边各自移动，新增重叠。本轮：新方案 +62,336 m²（现行方案 +193,593 m²），被覆盖面积净减 0.22% | 面积统计重复或遗漏；不符合"覆盖"的假设 | 短期在报告里如实写明；中期对同一成果内的图斑做一次共边处理（拓扑归一），或简化时以公共边为约束 |
| 7 | Shapely / GEOS 升级 | 生产固定在 Shapely 1.8.5.post1 / GEOS 3.10.3。上一轮在一次性容器里试过 Shapely 2.1 / GEOS 3.13（`coverage_simplify` 三种用法），没有采用 | 拿不到新版 GEOS 的确定性改进与新算子 | 单独立项：先在不改方案的前提下换版本重跑定稿回归，对比数字，再决定 |
| 8 | Coverage 编辑 | 编辑流程默认成果是"覆盖"（图斑不重叠、无缝），但没有强制；GEOS 把多数生产成果判为"不是有效 coverage"，所以用不了 `coverage_simplify` | 编辑不能保证相邻图斑共边 | 与第 6 项一起解决 |
| 9 | GEOS 的非确定性 | GEOS 3.10.3 的拓扑保持简化对少数退化输入不确定：旧方案全量 144,176 个里 23 个两次结果不同，三个数 137,040 / 137,041 / 137,042 就是它造成的。新方案加了精度门槛与重试之后，全量连算两次 0 个不同，那 8 个不稳定图斑各 100 次都稳定——但根因在 GEOS，不在方案 | "同一个操作每次结果完全一样"没有保证 | 在方案层面已经被门槛挡住；根因随第 7 项解决 |
| 10 | 顶点拖动有约 12 像素的死区 | 位移在 (10, 6) 像素以内不被识别并退出顶点模式，(12, 7) 以上生效且多移 3–5 像素。上一轮的构建上数值完全相同 | 小幅调整顶点做不准 | 绘制库的顶点模式行为，需要单独定位 |
| 11 | 贴矿山边界的大图斑多数无法简化 | 1,000 m² 以上近一半被拒，10,000 m² 以上 87% 被拒；与别的面取并集时也会因超出矿权范围被拒（演练里实际遇到） | 最大的图斑反而享受不到简化 | 与第 3 项一起看：边界来自像元掩膜 |

## 9. 未测与需要说明的

- **演练栈不带推理 worker**（要 GPU 和 4.5 GiB 内存）。权重挂载之后只核对了大小与文件数，**没有真的跑过推理**；
  上线后请人工跑一条小影像。
- 没有在容器内重算运行时资产的 SHA256（`verify_release.sh --hash-assets`），只比了大小和文件数。
- "候选构建 × 基线后端"这一格用的是去掉 turf 之前的候选构建；最终构建的前端源码与之相同，只少了三个没有代码引用的包，
  没有重跑。
- 多用户并发只在接口层测了（8 个会话同时校验、简化；两人同时保存）；没有多个真实浏览器同时编辑同一条成果。
- 切换之后 Miner 界面没有做真实浏览器检查，只核对了首页可达与健康。Miner 的代码本轮没有改动，但切换会把它的两个容器
  一并落到发布目录的版本。
- 在这台机器之外的环境（Linux 宿主、别的 Docker 配置）没有测过。
- **合并之后不要随手执行 `docker compose … up -d`**：compose 文件变了（多了资产挂载），它会重建后端与两个 worker。
  要上线就走 `deploy/switch_release.sh`。
- **我的只读扫描对生产 MySQL 的负载**：为生成沙盒 52 的清单，对库的每个文本列做了几轮全表 `LIKE` 扫描。

  随后回落到约 750 MiB，健康接口始终 200。这类全表扫描以后不再在生产库上做。
