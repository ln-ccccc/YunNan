## 批次 J：体验与性能快改

### J-1 缺失瓦片返回透明 PNG（根治锯齿边 404）

- 问题：底图覆盖为锯齿边（z15 矩形内缺口 96% 在边缘），bbox 过滤挡不住，地图控制台仍有 404（项目 10 实测剩 3 个）。业界标准做法为 bounds 内缺瓦片回 200 + 透明 PNG（MapLibre #1845、OSM 惯例）。
- 主模块：`miner/server.js:87-102`（项目瓦片路由）。
- 改法：`fs.existsSync(tilePath)` 为假时，若 `fs.existsSync(path.join(tileRoot, z))`（该 zoom 目录存在=资源确实切到此级，仅个别瓦片缺失）→ 返回常量 1×1 透明 PNG（模块级 Buffer 缓存）+ `Cache-Control: public, max-age=86400`；zoom 目录不存在或 `.active` 缺失仍 404（资源级错误不被掩盖，R3 瓦片巡检语义不变）。
- 验证：`miner/test/` 新增路由用例（临时目录伪造 zoom 目录：缺瓦片→200+PNG 魔数+缓存头；zoom 目录缺失→404；`.active` 缺失→404）；真实栈项目 10 地图复测 404=0。
- 预估：0.5 天。

### J-2 stats 接口提速（实测 7.98s）

- 问题：`GET /api/projects/1/stats` 实测 7.98s，每次打开看板全量重算，违反"概览读取及时反馈"底线（AGENTS.md §10）。
- 主模块：`backend/applications/project_hub/project_map.py:218` `get_project_stats`。
- 改法（两步）：
  1. **先 profile 定位**：容器内 cProfile 跑一次，确认大头（候选：每特征 shapely 面积回退、change_area 读盘、`_project()` 全量 ORM 加载）。若为单点热点（如面积计算）直接修热点；
  2. 无论热点为何，加**项目维度缓存**：结果挂在进程内 `{project_id: (computed_at, payload)}`，TTL 10 分钟 + 写路径失效（项目 archive/restore/矿山导入/推理发布时清除对应键——挂在既有 `_append_activity` 或各自 service 入口处）。
- 验证：新增单测（同请求两次第二次 <50ms；写路径后缓存失效）；真实栈项目 1 连续三次 stats 实测首次 <8s、后续 <100ms。
- 预估：1 天（含 profile）。

### J-3 分析 API 缺 fid 参数返回 400（现为 404 误导）

- 问题：`mines/indices`、`mines/change-matrix`、`mines/original-imagery` 缺 `fid` 时经 `int(None)` ValueError → 业务 404，实测误导排查（search 参数名 `q` 的教训同类）。
- 主模块：`backend/applications/api/project.py:540/551/668` 三路由。
- 改法：路由层显式 `fid = request.args.get("fid"); if not fid: return fail_api("缺少参数 fid", status=400)`；service 层不动。`trend-report` 无 fid 是合法路径（读 summary）不改。
- 验证：`test_project_map` 新增三处缺参 400 断言；真实栈 curl 复测。
- 预估：0.5 天。

### J-4 推理门槛 400 携带具体缺项（现文案不指明原因）

- 问题：底图未激活/worker 加载窗口时创建推理任务返回"项目当前不满足启动推理条件"，不指明缺哪项、无 worker 加载中提示（10-27 上午两次踩中）。
- 主模块：`backend/applications/project_hub/inference_inputs.py:142`（抛错处）；`miner/src/components/InferenceModal.vue`（文案映射）。
- 改法：抛 `ProjectInferenceInputError` 时附带 `details={failed_checks: [reason_code…], worker_status}`；API 层透传；InferenceModal 把 reason_code 映射为中文（沿用 22278fc 的 8 个降级码映射表新增条目：如 `NO_ACTIVE_BASEMAP`→"底图未激活"、`worker_loading`→"推理服务正在加载模型，请稍候"）。worker 加载窗口：capabilities 的 `worker_status=stale` 时门槛文案单独提示。

## 批次 K：正确性与韧性

### K-1 趋势报告接口激活（现为死接口）

- 问题：`GET mines/trend-report` 实测恒 `available=false`。代码查证：`project_map.py:337` 只读 `outputs/trend_reports/{summary|fid}.json`，**全仓库无任何生成方**——接口永远不可用。而 traceability 能现场聚合 ratio_series（indices+change_matrix 文件均存在），数据齐备。
- 主模块：`backend/applications/project_hub/project_map.py:337`、`mine_traceability.py`（复用其聚合逻辑）。
- 改法：`get_project_trend_report` 改为**现场聚合**：扫描 `outputs/indices/*.json` 的年份并集，逐 fid/汇总计算与 traceability 的 ratio_series 同源序列；文件不存在时不再依赖 `trend_reports/` 目录（保留兼容：若该目录存在则优先）。summary 形态返回 `{available: true, years: [...], series: [...], fids: n}`。
- 验证：新增单测（双年 fixture 断言序列值与 traceability 一致；空项目 available=false）；真实栈项目 1 fid713 复测 available=true 且与 traceability.ratio_series 数值一致。
- 预估：1.5 天。

### K-2 推理发布段尊重取消标志

- 问题：实测取消已受理（cancel_requested=true）但推理段完成后**发布段照常发布全部成果**（8 fid 全写入）。取消语义应在发布前再次检查。
- 主模块：`backend/applications/inference/worker.py:427`（`is_project_job and summary.get("written_fid_list")` 分支前）。
- 改法：发布分支入口增加取消检查：重新读 job（`self.job_store.get_job(job.id)`）若 `cancel_requested` 且当前状态仍 running → `finish_job(status="cancelled")` 跳过发布（推理产物留在 work_dir，不入正式成果）。
- 验证：单测 mock job_store（cancel_requested=True + pipeline 成功返回 → 断言未调用 publisher 且终态 cancelled）；真实栈复测 4s 取消场景 written=0。
- 预估：0.5 天。

### K-3 CPU 兜底前宿主内存预检（新增 INSUFFICIENT_HOST_MEMORY_FOR_CPU）

- 问题：实测强制 `device=cpu` 在 8GB 宿主 100% 失败（GPU 模型常驻 2.6G + CPU 加载峰值 4G > VM 5.79G），以推理深处 Errno 12 失败、浪费整个冷加载时长。R1 已正确归因，但应**前置失败**。
- 主模块：`backend/applications/inference/device.py`（R1 分类体系内扩展）、`worker.py` CPU 路径入口。
- 改法：CPU 模型加载前读 `/proc/meminfo` 的 `MemAvailable`，若 < checkpoint 体积×2.2（1.97G×2.2≈4.4G）→ 不进入加载，任务直接 `failed/INSUFFICIENT_HOST_MEMORY_FOR_CPU`，错误信息说明"宿主可用内存不足，无法加载 CPU 模型（GPU 常驻时尤为明显）"。显式 CPU 任务与回退路径均接入。
- 验证：单测 mock meminfo 两档（充足/不足）断言放行/拒绝与错误码；真实栈 device=cpu 复测：秒级失败带明确错误码（而非 60s 后 Errno 12）。
- 预估：1 天。

### K-4 取消竞态前端提示（低优先级）

- 问题：GPU 快任务（<10s）实测"取消已受理但任务照样 succeeded"，用户感知矛盾。
- 主模块：`miner/src/components/InferenceModal.vue`。
- 改法：cancel 请求返回后若任务已 terminal（succeeded），提示"任务在取消生效前已完成，成果已保留"；轮询终态为 succeeded 且曾发起取消 → 同文案。
- 验证：组件测试（mock 序列：cancel→succeeded 断言提示出现）。
- 预估：0.5 天。

### L-1 重启时序 502 窗口收敛

- 问题：实测 backend 重启约 40s 就绪窗口内 BFF 已放行 → authGuard ECONNRESET → 前端卡"登录中"无重试提示。
- 主模块：`docker-compose.prod.yml`、`miner/services/authBackend.js`。
- 改法：①compose 中 miner-api 增加 `depends_on: backend: condition: service_healthy`（现仅为启动顺序）；②`authBackend.js` 对 ECONNRESET/ECONNREFUSED 做 1 次短重试（300ms）再 502；③Miner 登录页对 502 显示"服务正在启动，请稍候重试"而非无限"登录中"。
- 验证：`docker compose config` 校验；真实栈 `docker restart yunnan-backend` 后 10s 内经 BFF 登录，断言重试生效或得到明确文案。
