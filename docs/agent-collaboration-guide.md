# YunNan 新生协作指南：边界、开发规范与生产力工具

本项目采用人主导、Agent 辅助实现的开发方式。人负责理解需求、确定路线、拆分任务、判断优先级和验收；Agent 协助读代码、实现、排查问题和运行测试。

不要求从零手写全部代码，但必须理解自己模块的输入输出、关键调用关系和验收依据，能看懂主要 diff、错误日志和测试结果。学习代码基础仍有必要；不能把 Agent 的解释通顺等同于实现正确。

本指南面向两人协作：项目负责人主导路线、边界和最终合并，协作者承担分配的模块任务。先读 [开发规范](development-standard.md)，每次换 Agent 让它读 [AGENTS.md](../AGENTS.md)。本指南是操作手册，不另建一套架构契约。

## 1. 开工前先理解需求和优先级

先熟悉这条业务链：项目建档 → 矿山/底图准备 → 登记影像 → 固定模型推理 → 矢量成果 → GeoView 人工编辑 → 保存、重开与导出。能说明当前任务服务哪个环节，再开始编码。完整流程不必每次都从头运行，但不能不知道上游和下游。

由负责人维护一份任务列表，GitHub Issue 或现有 Markdown 列表即可，不额外建设管理平台。每项写清优先级、负责人、验收和依赖，按下表取舍：

| 优先级 | 本项目的判断依据 | 时间不足时怎么办 |
| --- | --- | --- |
| 必须先做 | 核心链路阻塞、跨项目串数据、保存丢失、正式成果错误 | 优先修复并验证；不能因赶进度省掉持久化与数据正确性验证 |
| 本轮应做 | 失败恢复、常规规模性能、影响验收的交互问题 | 先处理影响最大的场景，用实测决定优化点 |
| 可以后排 | 非必要视觉润色、额外格式、便利性扩展 | 由负责人明确延期，不悄悄塞进当前 PR |

上述是任务优先级，不替代架构文档中的实施阶段编号。计划写估计工作量和主要不确定性，不把 Agent 的预计耗时当承诺；实际超过预估时及时重排。

本期不做在线训练/模型重训、React 重写、浏览器 GB 级上传和切片、多人实时 GIS 编辑，也不承诺未经评估的精度。大底图沿用离线目录登记与后台切片路线。新需求先确认是否影响交付，再安排开发。

## 2. 谁决定什么，哪里需要同步

负责人拥有决策权，不代表所有代码都必须由负责人亲自写。同学可以在确定的边界内自主推进，无需对每个函数和每次测试重复申请。

| 边界 | 协作者可自主完成 | 需要负责人先确认 |
| --- | --- | --- |
| 需求与优先级 | 实现任务卡已确定的场景，报告发现的问题 | 增减功能、改变验收口径、调整交付顺序 |
| 模块内部 | 组件内部实现、相关样式、局部函数、对应测试 | 改模块职责，跨模块搬业务逻辑，重构无关目录 |
| 公共契约 | 消费现有 DTO、事件、API 与错误码 | 新字段、事件语义、API、状态含义或持久化格式变化 |
| 数据与算法 | 使用小样例验证既有逻辑 | 数据库结构、正式成果写入、类别、CRS、预处理、权重与精度口径变化 |
| 依赖与环境 | 使用锁定依赖、已有开发环境，查看日志 | 新增/升级依赖、共享 Compose/挂载、开放网络、生产操作 |
| 交付 | 自查、测试、提交自己的任务分支、发起 PR | 合并 `main`、发布部署、数据迁移或恢复 |

任务卡已经明确授权的跨模块接线不必再次申请；发现超出原授权的影响才同步。一个任务有一个主模块，不等于只能改一个文件夹：必要的调用方接线可以同 PR，但须列明，不能为了“单模块”复制业务逻辑。

本项目容易混淆的边界如下，实际位置与独立测试方法见 [开发规范第 2、3 节](development-standard.md#2-模块边界与低耦合)：

- Miner 负责项目工作台和入口，消费公开 DTO，不自己计算项目就绪规则。
- Miner BFF 负责同源转发和轻量适配，不做 GIS 运算和项目业务判断。
- 项目后端拥有生命周期、readiness、资产只读模型与业务动作规则。
- 空间模块拥有矿山、底图、切片与激活；推理模块拥有固定模型执行与暂存输出。
- 成果模块拥有正式成果、修订与导出；GeoView 负责推理后矢量编辑交互，通过成果 API 保存，不能直接改正式文件或自动基线。
- 部署模块拥有镜像、挂载与运行环境，不在部署脚本里修改业务规则。

低耦合的检查方法：说清本模块接收什么、返回什么、谁负责写数据；能用小样例替代外部依赖独立调试；改内部实现时不迫使无关模块一起修改。不为低耦合预先增加微服务、插件系统或多层空壳封装。

## 3. 开始前确认你正在改哪份代码

在你准备工作的仓库目录运行：

```powershell
Get-Location
git branch --show-current
git rev-parse --short HEAD
git status --short
git worktree list
```

把工作目录、分支和任务写进首条消息。若有不认识的未提交修改，先弄清归属；不要让 Agent 自动 reset 或覆盖。

`agent.md` 是手动阅读入口，`AGENTS.md` 是本仓库统一维护的项目规则。不同工具是否自动读取由工具决定；最稳妥的方式是明确要求读取，并让它指出实际主模块和测试入口。平台规则若需单独设置，只引用仓库规则，不复制一整套长期维护。

## 4. 用一张短任务卡下指令

每次单个模块开发前填写任务卡。任务卡可直接放在 Issue/PR 描述，不要求每次新建一份计划文件。编码可以交给 Agent，任务目标、模块边界和完成依据必须由人想清楚。

```text
工作目录/分支：填写实际值。
负责人/优先级：填写实际值；优先级由项目负责人确定。
目标：用户做什么操作，现在怎样，期望怎样。
主模块：例如 GeoView 分类成果编辑器。
输入/输出：依赖哪些公开数据或接口，向谁提供什么结果。
允许范围：相关组件、API 适配与对应测试；需要越界先说明原因。
需要先同步：本任务尚未授权的接口、状态、存储、共享文件或部署变更。
约束：沿用现有接口与 Vue，不调整模型/类别/原始影像，不加无需求的新层。
验收：给 2～4 条可操作、能判定结果的场景。
验证：准备哪些小样例，运行哪些现有测试，浏览器如何重走。
授权：本次是只分析、直接修复，还是计划经我审核后实施。
交付：一个聚焦任务的 PR，附实际验证和未测项；由负责人合并 main。
请先阅读 AGENTS.md 与相关契约，指出调用链后按上述授权推进。
```

小 bug 可以直接授权“复现后修复并验证”；跨模块新功能先看短计划。不要每一行改动都审批，也不要只发“全面优化全部代码”。

项目资产面板示例：

```text
任务：完善项目资产面板的加载与错误恢复。
负责人：协作者。优先级：本轮应做。
工作目录/分支：开工时填写实际值。
主模块：Miner 项目资产面板及对应测试。

输入：已有公开资产 DTO、loading、error、filters。
输出：展示资产；发出筛选、刷新等现有事件。
可独立修改：面板内部逻辑、样式、提示和相关测试。
需要先同步：新增接口字段、改变父子组件事件、修改项目就绪规则。

验收：
1. 正常、空数据、加载中、失败四种状态可辨认。
2. 刷新后能恢复，切换项目不显示上一项目的数据。
3. 不新增重复请求，不在面板内拼服务器路径。
4. 提供相关测试、构建结果和浏览器操作证据。

验证：以四态 fixture 独立调试，再在真服务下切换项目、触发失败并恢复。
若根因在父组件的数据请求层，先说明影响，不在面板内复制请求逻辑绕过。
交付：一个聚焦该任务的 PR，提交名称浅显易懂；由负责人合并 main。
```

## 5. 用具体场景指挥 Agent

以下是练习任务的写法，并不是声称当前仓库仍有这个 bug：

```text
主模块：frontend/src/ 的 GeoView 分类成果编辑。
问题：假设我修改一个面的类别，保存后重新打开却显示旧类别。
目标：成功保存后读到新版本；保存失败时保留本地编辑并显示原因。
先检查 AGENTS.md、矢量成果契约、编辑器和保存 API 调用链。
先复现并判断是前端 payload、后端持久化还是重读造成，不预设后端一定错。
允许修复已确认根因及必要消费者，保持现有类别代码和版本接口。
验收：改类后保存重开一致；旧版本保存遇到 409 不覆盖；自动基线不变。
运行相关 Node/Python 测试及前端构建，浏览器走一遍保存重读。
本次已授权直接修复，不新增自动保存或自动冲突合并。
```

正常推进顺序：Agent 定位调用链 → 复现 → 修改 → 对应测试 → 浏览器重走 → 交付。你检查失败是不是同一个问题、修复是不是改变了错误的模块、保存结果是否真正可重读。

让它分析、实施、优化或审查时，分别说明授权和证据要求：

| 想做的事 | 推荐指令重点 | 你应拿到的证据 |
| --- | --- | --- |
| 分析方案 | “先只读，列实际调用链、两种以内可行做法、最小验证，再给建议” | 文件依据、影响面和取舍，不是凭文件名猜架构 |
| 按计划实施 | “按已确认方案直接实现，普通测试自行执行，遇到范围扩大再说明” | 可运行改动、测试输出、关键 diff |
| 查 bug | “用我的步骤复现，说明输入/预期/实际，定位根因后修” | 修前失败、修后正常；未复现就不能宣称根因确定 |
| 提升速度 | “固定同一数据和环境测基线，定位最慢环节，改一处后同条件复测” | 输入规模、前后耗时/资源/失败数；不能只报感觉更快 |
| 独立审查 | “只审这个分支相对基线的改动，找能复现的功能/数据/性能回归” | 问题位置、触发条件、影响；不要为凑建议重构 |
| 换 Agent | “根据下面交接内容核对 Git，继续未完成项，不重复已验证且未变动工作” | 正确工作树、任务剩余边界、下一条具体动作 |

性能任务示例：

```text
只处理“切换项目很慢”。先在同一参考机、同一常规档数据测 20 次切换，
记录 p95、请求数量和最慢请求，区分后端查询与前端渲染。
按 development-standard.md 的目标评估，优先修实测瓶颈；
不改变项目就绪规则、不删除数据来提速、不提前增加缓存服务。
修改后同条件复测，附具体前后数据和功能回归证据。
```

## 6. 两个人、多个 Agent 怎么独立推进

负责人和协作者各负责一个当前任务的主模块，分别管理自己的 Agent 和工作分支。任务结束可以换模块，不要求永久一人前端一人后端。新生优先从资产、活动等边界清楚的面板开始，熟悉后再承担空间或成果任务；不要一开始授权“随意修改整个 miner”。

每人使用独立工作目录和分支（独立 clone 或 worktree 均可），不能在同一目录里同时切分支开发。新任务分支默认使用 `codex/<模块>-<任务>`，保留已有分支命名。起点由负责人指定并记录提交号，不能假设 `main` 已含另一人的未合并接口。普通独立任务基于已同步的 `main`；存在前置依赖时先约定 fixture 或等依赖合入，不悄悄把整条功能分支并入自己任务。

共享入口、路由、API client、数据库模型、锁文件和 Compose 同一时间由一人主改。需要跨这些文件时在任务卡注明；接口先给字段和成功/失败样例，双方围绕同一份契约开发。

例如开发矢量保存：甲先约定后端成功、409、422 示例；乙用这些小样例调 GeoView；甲用临时数据库测修订；最后合到同一测试环境，保存后关闭页面再打开。mock 让双方能独立推进，真实联调才证明边界连上了。

接口临时不通时，先查“进程是否启动、地址/端口、会话 cookie、HTTP 状态、返回字段”，不要让 Agent 随便改 CORS、关闭鉴权或打开新端口。联调使用独立测试库和输出目录，模型/镜像共享但不要一起写同一份结果。

Git 只放源码、锁文件、文档、小型合成样例和测试；权重、镜像 tar、原始影像、瓦片、数据库卷和真实密钥按现有离线资产方案交接，不放 PR。权重和原始影像只读共享，各自隔离端口、测试数据库、运行输出和 Docker 可写卷；只改容器名字不等于数据已经隔离。同一块 GPU 的重任务约定时段，避免互相占满显存。

## 7. 测试与验收：怎么知道真的做完

协作者负责本模块验证和自查，负责人负责最终验收与合并。新手至少会区分以下测试，而不是每次盲目跑全仓：

| 方法 | 证明什么 | 本项目练习 |
| --- | --- | --- |
| 单元测试 | 一个函数或规则在给定输入下行为正确 | 资产状态映射、编辑 payload、空值与无效输入 |
| 接口/契约测试 | 请求、字段、错误码与消费者约定一致 | 正常、空、参数错、未登录、跨项目和失败返回 |
| 集成测试 | API、数据库、文件或服务之间真的连上 | 保存修订后重新读取；失败不留下半份成果 |
| 浏览器流程/回归 | 用户操作能够完成，原有功能未破坏 | 加载/空/失败/恢复，切项目，编辑保存后重开 |
| 性能比较 | 同样条件下速度和资源是否退化 | 记录同输入、同机器的前后耗时、请求数、失败数 |

按 [开发规范第 6、7 节](development-standard.md#6-测试按风险选择) 选择现有命令。UI 逻辑通常运行对应前端测试、构建和浏览器操作；后端规则选择相关单元/集成测试；纯文档做链接和 diff 检查即可。测试依赖缺失导致跳过时单列原因，不把退出码为 0 当作全部场景已测。

mock 可以帮助独立开发，但不能替代真实保存、真实 worker 或真实 GPU 验证。修改推理执行/发布链路时补同权重小 TIFF 真运行；只改资产面板不要求重跑模型。性能目标见开发规范，目标不等于实测达标；不得通过改变预处理、类别或静默简化正式矢量提速。

至少问自己五个问题：

1. 它改的是我提的场景吗？有没有顺带改训练、框架、类别或接口？
2. 它能解释数据从哪里来、在哪里保存、谁决定状态吗？
3. 我能用给定步骤亲手看到结果吗？保存后重开、下载后打开都算。
4. 测试是在正确分支运行的吗？mock、真服务、真 GPU、性能实测分清了吗？
5. 未做完的部分写清楚了吗？下一位同学能继续吗？

常见纠偏方式：

| Agent 的表现 | 你的纠偏指令 |
| --- | --- |
| 为小功能增加多个管理层或过渡版本 | “用现有组件/服务直接完成，说明新增层不可替代的必要性，否则收回。” |
| 只有 build 通过就说流程顺畅 | “补一次真实页面操作与保存重读，列尚未覆盖的路径。” |
| mock 成功就说 4070 可正常推理 | “把 mock 与真实运行分开，核对 worker、权重和设备，未测就注明。” |
| 为测试通过而降低断言或吞异常 | “保留业务预期，修根因；若原预期有误，用契约证据说明。” |
| 未测就说性能优化了 | “提供同输入、同设备的前后耗时；否则只能称实现调整。” |
| 不断询问已授权的小步骤 | “现有授权内直接继续，只有新产品选择或高风险越界再确认。” |

不要为了项目显得顺利让它删除失败日志、隐藏未测项，或者编造模拟数据作为成果。遇到不懂的 diff，可以要求逐段解释“这段解决哪个验收条件”。

## 8. PR 和完成通知

正常流程：任务卡明确范围 → 独立分支 → Agent 调查与实现 → 自查 diff 和对应测试 → 发起 PR → 负责人评审 → 负责人合并 `main`。计划审核只在任务卡要求或遇到新决策时进行，不添加多轮形式审批。

每个可独立验收的模块任务提交一个聚焦的 PR。PR 可以包含多个小提交，不要求一个提交写完；也不要积攒多个无关模块才一起提交。提交信息尽量说明用户价值，例如 `fix(资产面板): 加载失败后可刷新恢复`，避免只写“update”“优化一下”。

请求最终评审与合并前：

1. 检查当前分支、`git diff --check`、逐文件 diff 和已暂存内容，只提交当前任务文件。
2. 复核 PR 相对目标分支的完整差异，避免夹带前置分支未合并内容；同步最新基线后对受影响场景重测。
3. 在 PR 中写清任务卡、主模块、必要关联修改、接口/数据影响、实际测试命令及结果、未测项；界面变化附截图或短录屏。
4. 自己能解释关键改动、能亲手演示验收路径，再请求负责人评审。Agent 的自查可以辅助，不能替代人的判断。

PR 描述使用 [开发规范第 8 节](development-standard.md#8-pr复核与交付) 的短模板。通过/失败/跳过/未执行分别记录；需要提前讨论或交接时可以发草稿 PR，写明待验证内容，不能作为可直接合并的完成项。

日常完成通知只需两行，详细证据保留在 PR：

```text
已完成：项目资产面板加载与错误恢复。
分支：codex/assets-recovery（示例，交付时填真实分支名）。
```

需要时可附 PR 链接，不必重复长篇实现过程。协作者和 Agent 不直接推送或自行合并 `main`，不擅自发布；由项目负责人决定合并、取舍和部署。

“自己搞懂再提交”不等于无限排查或隐瞒问题。缺需求决定、权限、数据或发现越界时及时发：`阻塞现象 → 已检查内容/证据 → 需要负责人决定什么`。普通修复自行推进；同一失败反复出现时重新查假设，不盲目重试或随意扩大修改范围。

## 9. 需要学习的技能与生产力工具

### 9.1 技能树：学到能操作，不先学完整技术栈

| 技能 | 最低需要掌握 | 达标练习 |
| --- | --- | --- |
| Git | 工作区/暂存区/提交/分支；status、diff、log、fetch、switch、add、commit、push、PR；理解 merge 与冲突 | 在练习分支提交一处修改，检查完整 PR diff；在试验仓库解决一次冲突和撤销一次错误提交 |
| Docker | 镜像与容器区别、端口、环境变量、绑定挂载与卷；Compose 启动、日志、状态、重启 | 在独立测试环境启动项目，定位一次启动失败，重启后确认测试数据仍在 |
| Coding Agent | 给上下文、写任务卡、区分只读/计划/实施授权、查阅规则、审 diff、控制上下文和交接 | 让 Agent 修一个小问题，指出它改了什么、为什么改、怎么验收 |
| 测试 | 复现、正常/异常/边界样例、单元/接口/集成/浏览器回归、mock 与真实环境区别 | 提供修前失败、修后通过及保存重读证据，解释未测范围 |
| 最低技术基础 | 读懂模块涉及的 Vue/JS 或 Python 关键代码；HTTP、JSON、异步请求和状态码；会看浏览器 Network/Console | 追踪一次点击到 API 和保存位置，判断错误发生在前端、BFF、后端还是 worker |
| GIS 基础（接空间/成果任务前） | 栅格/矢量、CRS、经纬度顺序、像素/波段/NoData、FID、类别代码、结果与修订区别 | 说明影像为什么可能错位，能核对编辑前后类别、几何和成果来源 |

不用先学完所有框架、算法和 Docker 原理才开始工作，但不能跳过当前模块的关键概念。Git 学会看差异后再学撤销；不把 `reset --hard`、强制推送或删除卷当作日常纠错方式。

学习入口：[Pro Git 中文版](https://git-scm.com/book/zh/v2) 先读“Git 基础”和“Git 分支”；[Docker 入门](https://docs.docker.com/get-started/) 先读容器、镜像、端口与存储。按上表完成练习，不要求通读整本资料。

### 9.2 最小工具组合

- 编辑器与终端：沿用熟悉的编辑器，用于搜索、阅读关键代码和 diff；PowerShell 用于运行实际命令。
- Git 与 GitHub PR：管理源码、任务和审阅证据。源码版本和本地运行数据分别管理。[PR 官方说明](https://docs.github.com/en/pull-requests/reference/pull-requests)
- Docker/Compose：复用现有运行环境，避免每个人临时安装一套不同的 GIS 依赖。
- Claude Code：作为当前优先试用的 coding agent；Agent 工具和背后的模型供应商是两个选择。
- 浏览器开发者工具：Network 看请求/响应/耗时，Console 看报错，Performance 排查卡顿。先练习 [Network 请求排查](https://developer.chrome.com/docs/devtools/network/)。
- 现有 Node/Python 测试与小型 fixture：日常开发优先使用，不为工具齐全先引入新测试框架。

Docker 初期重点认识以下命令的作用；占位项必须替换为负责人约定的独立开发环境，不能直接复制操作共享/生产服务：

```text
docker ps                         查看容器状态
docker images                     查看已有镜像
docker logs --tail 100 <容器>       查看近期日志
docker stats                      查看运行资源
docker compose -f <配置> -p <开发项目名> ps
docker compose -f <配置> -p <开发项目名> logs --tail 100 <服务>
docker compose -f <配置> -p <开发项目名> up -d
docker compose -f <配置> -p <开发项目名> restart <服务>
```

先核对挂载、端口和数据库配置；`-p` 不保证共享绑定目录和固定端口自动隔离。查看日志/容器配置时注意脱敏，不把环境变量中的密钥粘到聊天或 PR。

### 9.3 Claude Code 与 GLM 的使用策略

当前建议按团队成本和习惯优先试用 Claude Code，日常开发考虑接入 GLM Coding Plan。这里是本项目的试用策略，不是模型排名，也不承诺 GLM 能独立处理所有复杂任务。

截至 2026-09-05，智谱官方提供 Claude Code 的 GLM 接入说明，并说明界面模型名称可能经过服务端映射；使用 Claude Code 不代表实际调用的一定是 Claude 模型。先按官方说明核对客户端版本、实际模型映射、端点与套餐 Key，再试读文件、局部修改和运行测试的完整工具链，不能只测试聊天回复。[智谱接入说明](https://docs.bigmodel.cn/cn/guide/develop/claude)

Coding Plan 有限定的工具和使用范围，配置错误端点可能无法使用套餐额度。不要把编程订阅当作本项目业务后端可任意调用的通用 API 额度。价格、配额和支持范围以开通时官方说明为准；不在开发规范中固定套餐价格，不转借个人 Key。[套餐快速开始](https://docs.bigmodel.cn/cn/coding-plan/quick-start)

用本项目三类小任务做试用验收：一个面板四态处理、一个接口失败测试、一处已有 bug 修复。比较是否遵守边界、diff 是否可理解、测试是否真实、人工返工量与总耗时。涉及 GIS 正确性、版本冲突、路径安全、跨模块设计或持续定位失败时，由负责人重点复核，必要时换模型；换模型后仍要验收。

模型接入不得上传真实客户影像、权重、生产数据库或密钥；私有源码与客户资料能否发送给外部模型服务也须由负责人先确认。本文未配置 API、购买套餐或验证本机 Claude Code + GLM 的实际运行。

Claude Code 初期掌握几个入口即可：`/help` 或 `/` 查看当前版本命令；`/status` 查会话状态；`/permissions` 查看权限；`/compact` 压缩当前上下文；`/clear` 开始新上下文；`/resume` 恢复会话。清上下文前写交接，命令不等于代码回滚。先说明“只分析”或“按已确认任务实施”，不要默认开放所有命令权限。[Claude Code 命令说明](https://code.claude.com/docs/en/commands)

### 9.4 规则与 skills：先少量用好

Claude Code 原生读取 `CLAUDE.md`，不能假设会自动读本仓库的 `AGENTS.md`。后续接入时可在项目根的 `CLAUDE.md` 中导入统一规则：

```text
@AGENTS.md
```

随后用 `/memory` 或 `/context` 检查加载情况，并让 Agent 说明本次边界；规则文件是指令上下文，不是能强制阻止误操作的权限系统。本次仅提供接入写法，未创建 `CLAUDE.md` 或修改个人配置。[Claude Code 规则加载说明](https://code.claude.com/docs/en/memory)

Skill 是可复用的任务步骤和检查要求，不是安装后必然正确的能力。Claude Code 的项目级 skill 通常位于 `.claude/skills/<名称>/SKILL.md`；具体触发与权限以已安装版本和 skill 内容为准。[Claude Code skills 说明](https://code.claude.com/docs/en/skills)

先掌握四类工作方法：需求与范围梳理、按证据排查 bug、完成前验证、只读审查 diff。需要时再由负责人选少量可信 skills；上述是方法类别，不保证当前工具已经安装同名 skill。安装前读清是否运行脚本、联网、写文件或扩大权限，不盲装“大礼包”。本项目规则和用户授权不能被第三方 skill 扩大。

不必一开始学习 MCP、hooks 或多 Agent 自动编排。先让单个 Agent 完成一项可复核任务，再考虑并行只读审查；真正同时写代码时，按第 6 节隔离工作目录。

## 10. 换 Agent 的最小交接包

无需复制整个聊天记录。把以下内容放在 PR、任务说明或一个该任务专用的交接记录里，完成后以 Git 和正式文档为准：

```text
目标与已同意范围：
工作目录 / 分支 / 基线提交 / 最新提交：
本地未提交改动及归属：
已实现：关键文件、公共接口、用户可见行为。
已验证：日期、环境、命令、结果，说明 mock 或真实运行。
性能：数据规模、基线、结果；没有实测就写未测。
未完成/已知问题：复现步骤、原因是否确定、下一步。
运行条件：服务/端口、镜像 ID、权重标识、测试数据位置；不附密钥。
授权边界：是否可提交、推送、部署或改数据；已批准事项不重复申请。
必须读取：AGENTS.md、开发规范、目标模块契约。
请核对当前代码再继续；报告与代码不一致时指出差异，不盲信前任结论。
```

## 11. 给新生的第一次练习

建议用最初 2～3 个工作日完成一次小闭环；这是练习安排，不是零基础学生必然达到的工期承诺：

1. 熟悉需求和目录，让 Agent 只读追踪“登记影像 → 创建任务 → 返回成果”，你用自己的话解释各模块职责；在独立测试环境跑一次已有测试。
2. 填写一张任务卡，在自己的分支修一个负责人指定的小问题，演示修前失败、修后正常，读懂关键 diff。
3. 自查并提交 PR，附实际验证；请负责人审阅和合并。再用交接包换一个 Agent，确认它能说清已做、未做和下一步。

第一次练习不从全仓重构、依赖升级、模型训练或部署迁移开始。能清楚提出一个问题、看懂关键改动并完成验收，就已经建立了有效的协作方式。
