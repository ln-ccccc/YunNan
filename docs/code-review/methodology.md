# 代码审查与测试方法论（open-code-review 优先）

本文件是本仓库做 code review 与测试的**优先方法入口**，融合两套外部标准：

1. [alibaba/open-code-review](https://github.com/alibaba/open-code-review)（OCR）——确定性工程 × Agent 混合架构：精准文件筛选、智能文件分包、规则匹配、评论定位校验、评论反思。设计取向：**高准确率、低噪声（precision 优先于 recall）**。
2. [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills)——五轴审查（正确性/安全性/性能/可维护性/测试）、severity 标签、反合理化表、"验证不可协商"（修复必须附测试通过/构建输出/运行时数据证据）。

## 工具链

- OCR CLI（`npm i -g @alibaba-group/open-code-review`，本机已装 v1.12.7）：
  - `ocr delegate rule <files>` —— 委托模式，**无需 LLM 配置**，按语言组输出系统审查规则（Python / TS-JS / 默认三组，快照见 [ocr-system-rules-snapshot.md](ocr-system-rules-snapshot.md)）。
  - `ocr delegate preview` —— 预览可审查文件与模式元数据。
  - `ocr review`（diff 审查）/ `ocr scan`（全量文件扫描，适合审计陌生代码库）——需配置 LLM endpoint 后使用。
- 委托模式分工：OCR 负责**文件选择与规则解析**（确定性部分），宿主 agent 负责**逐文件执行审查**（阅读代码、核对规则、定位行号）。

## 七步流程

1. **分包**（smart file packaging）：按模块职责 + 语言 + 关联文件划分审查单元；关联文件（如 service 与其 API 层、测试与被测代码）归并同一单元，单元之间上下文隔离、可并行。单包 ≤ 约 6k 行。
2. **规则解析**：对每个包跑 `ocr delegate rule <代表文件>`，得到该包适用的系统规则组。
3. **执行审查**：包内逐文件**完整通读**（禁止抽样），按 OCR 规则 + agent-skills 五轴检查：
   - 正确性：边界/空值/异常处理/资源泄漏/并发（先确认并发上下文）；
   - 安全：路径遍历/SQL 拼接/命令注入/反序列化/密钥泄漏/鉴权绕过/XSS（先确认输入是否攻击者可控）；
   - 性能：N+1/无界加载/循环内重算/热路径（先确认数据规模与热度）；
   - 可维护性：死代码/重复逻辑/业务硬编码/命名；
   - 测试：关键路径覆盖的明显缺口。
4. **项目契约叠加**：在通用规则之上叠加 [AGENTS.md](../../AGENTS.md) 契约——模块边界与依赖方向、四层状态模型（lifecycle/readiness/asset/job 禁止混用）、路径只由存储服务生成、导出沙箱、前端只渲染 DTO、异常原文不外泄、镜像命名 yunnan 系。
5. **定位校验与反思**（OCR 反思模块思想）：汇总后**逐条亲自复核**——finding 必须核对到具体行号与数据流，安全/并发/性能类必须确认攻击面/调用上下文/数据规模，砍掉拿不准的。误报消耗信任，宁缺毋滥。
6. **修复与回归**：可判断的 P0/P1 直接修，跑该模块现有测试 + 新增回归；涉及跨模块契约的按"契约 → 提供方 → 消费方 → 集成验证"顺序；不能判断的进决策清单等负责人。
7. **报告与沉淀**：按 severity 分级汇报（改了什么/为什么/输入输出/验证/未测），新测试技巧沉淀进 [testing-playbook](../testing-playbook.md)。

## Severity 分级

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| P0 | 安全漏洞、数据损坏、必现崩溃/数据泄漏 | 立即修 |
| P1 | 正确性缺陷、契约违反、>20% 性能退化隐患 | 本轮修 |
| P2 | 可维护性问题、测试缺口 | 视情况修 |
| P3 | Nit（风格/微优化） | 记录，不强制 |

## 证据规则（反合理化）

- 每条 finding 必须有：`文件:行号` + 代码原文摘录 + 具体触发条件/数据流 + 建议修法。
- 禁止推测性报告："可能""或许"无证据不报；禁止"顺手重构"超范围改动。
- 安全类先验证数据源是否攻击者可控；并发类先确认多线程/多进程/异步证据；性能类先确认热路径与数据规模。
- **验证不可协商**：声称修好必须给出测试通过、构建输出或运行时数据，不接受"应该没问题"。

## 与仓库既有规范的关系

本方法论只规定"怎么审、怎么报"，不改变 [AGENTS.md](../../AGENTS.md) 的模块边界、提交与测试规范；冲突时以 AGENTS.md 为准。
