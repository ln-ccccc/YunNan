### 5.2 候选与回滚目录的完整核对

第一轮只比了大小和文件数。本轮加了容器内重算 SHA256，立刻查出问题：两个权重文件对得上，**5 个目录型资产（第三方源码目录和
4 个旧模型目录）全部对不上**。逐文件对比后确认：宿主机和容器里是同一批文件、内容完全一致，差别只在 2,995 个下载标记文件
名字里的一个字符（Windows 上是 U+F03A，挂进容器变成普通冒号），而指纹算法把文件名算了进去。

修在算法上（名字按容器里看到的算），不改任何资产内容；指纹算法升版本、旧缓存作废；两个发布目录重建。重建之后，候选与回滚目录
在演练栈上各做了一次完整核对，都是 55 项 0 不符。

这件事本身说明：资产内容没有问题，问题在核对工具。如果不做这一步，上线后第一次带 SHA256 的核对会报 10 项不符，容易误判成权重被换过。

它不在这次发布的范围内，我没有改；要不要修、谁在用，需要您知道后决定。

这里订正一处我自己的理解：一开始我以为推理 worker 也是起子进程用 MMSeg310 加载模型的，核对脚本因此对不准；读过
`applications/inference/worker.py` 之后确认，worker 是在进程内（`/opt/venv`）用 `init_model` 加载的。

### 5.4 切换脚本的失败安全

脚本顺序改为：核对发布目录 → 用目标目录渲染并对账 → 查进行中的任务 → 写 `.env` → 分阶段切换 → 核对。
前三步只读；写 `.env` 之后再渲染一次，必须与对账过的那份逐字节相同，否则立刻改回。

复查中查出并修掉的缺陷（每一个都只在失败时暴露）：

| 缺陷 | 后果 |
| --- | --- |
| 状态值多包了一层引号 | `--rollback` 永远判不成"上一次成功"，切换成功后回滚会回到当前这一份而不是上一份 |
| 没加 `set -E` | 意外失败的兜底在函数里不触发，脚本静默退出、不给恢复提示 |
| Python 进程按系统默认的 GBK 读写管道 | 普通终端里 `D:/项目/…` 进管道成了乱码路径，对账不通过（我的会话里恰好带着 `PYTHONUTF8=1`，所以此前没发现） |
| 首次切换（生产就是这种情况）失败后，恢复提示说回到基线，实际却去解除钉住回开发树 | 提示与行为不一致 |
| 切换状态文件按发布根共用 | 演练留下的记录会让生产的 `--rollback` 回错版本 |
| Ctrl-C 不走兜底 | 中断之后没有恢复提示 |

有界等待：查任务 30 秒；每次 docker 调用（含 `compose up`）5 分钟；容器内重算资产 SHA256 1 小时；每个阶段等健康 900 秒（可调）；
容器退出或反复重启立即判失败。

演练结果见第 1 节。逐项断言的驱动脚本与各步日志在交接目录 `zcode-20261124-release/scripts/round2_rehearsal.sh`、`out/round2/`。

### 5.5 备份与可恢复性

- **数据库**：`docker/backup_yunnan.sh` 用 `mysqldump --single-transaction`，不需停库。最近一次全量备份是
  `backups/yunnan_backup_20261106_150646`（7.8 GB）：5 个产物的 SHA256 与清单一致、压缩包校验通过、导出文件完整收尾、16 张表。
  但生产库现在有 17 张表（之后多了 `alembic_version`），数据也多了 19 天——**这份备份过时，不能作为这次的恢复点**。
- **成果存储**：同一份备份含 `project_storage`（不含可再生的底图与瓦片目录）。成果修订、审计、导出都在库里和这个目录里。
- **配置文件**：备份脚本**不含** `.env`、`image_bundle.env`；`config.yaml` 与 compose 文件在 Git 里。`.env` 要单独备份。
- **恢复演练**：没有做过整库恢复，本轮也没做（恢复 7.8 GB 会明显占用虚拟机磁盘，此前出过磁盘写满导致生产不可用的事故）。
  恢复流程见 `docs/backup-restore.md`。
- **本轮发现的一个恢复陷阱**：只恢复数据库、不恢复存储是危险的。库里没有种子项目的资源记录、而存储目录已存在时，后端启动脚本
  的迁移会因目录已存在崩一次（演练里实际遇到）。恢复时数据库与存储要按同一时点一起恢复。
- **这次发布对数据的影响**：没有数据库结构和模型的改动，没有迁移；代码回滚不写库、不删文件，上线后新增的修订与审计都还在。
  备份是"以防万一"，不是回滚的前提。

### 5.6 新增重叠的业务影响

- **数字**（全量 3,029 条成果、144,176 个图斑的模拟，对所有图斑都做一次简化）：图斑间新增重叠 62,336 m²（现行方案 193,593 m²）；
  被覆盖面积的净变化 −70,154 m²，即 −0.22%（现行 −1.06%）。按单条成果看，被覆盖面积的变化中位数 −12.5 m²，最差的一条 −434 m²
  （现行：中位数 −94 m²，最差 −771 m²）。逐条成果的新增重叠明细当时没有留存，只有合计和这些分位数。
- **什么时候发生**：只有用户在编辑器里选中图斑、点"消除锯齿"时。全仓库只有一个调用点（编辑器的 `simplifySelectedFeatures`
  → `geometry/simplify` 接口），没有任何自动的、整份成果的简化，也没有任何迁移或定时任务会改写已有成果。
- **对业务的影响**：按图斑分类别求面积时，重叠部分会被重复计入，上界就是上面那个数（占被覆盖面积的 0.2% 量级）；
  "被覆盖面积"会略微减小。类别归属、原始影像、自动矢量化生成的基线修订都不受影响。相邻图斑的公共边各自移动是重叠的来源
  （技术债务 6、8），本轮不处理，也不自动修改相邻图斑。
- **保护措施**：简化结果只在用户保存时成为新修订；自动矢量化生成的基线修订不变；保存冲突不会自动覆盖他人的修改。

### 5.7 独立面积复核里量不了的那一个

99,776 个"有变化"的结果里，99,775 个用等积投影独立重量过，没有一个超过 3% 的门槛。1 个（成果 243 的第 44 个面，77.5 m²，
带 3 个孔）重投影之后自相交，等积投影量不了。换一种量法补上：面积变化 +1.1701%、对称差 4.6745%，都在门槛内，与引擎自报一致。

准确的说法是"全部量过，其中 1 个换了一种量法"，不是同一种方法的 100%。已订正到对照实验报告 §9 和交付报告的勘误里。

## 7. 失败回滚条件与回滚步骤

**出现下列任一情况就回滚：**

1. 切换脚本在任一阶段失败，或收尾核对有不符项；
2. 上线后 10 分钟内，登录、成果列表、编辑器、Miner 工作台有打不开的；
3. 真实 GPU 推理验收（N3）不过：模型加载失败、显存不足、任务失败或超过 10 分钟没有结果、成果没有发布或打不开；

6. 数据出现异常：没有人操作时，已有成果的修订号或图斑数发生了变化；审计记录里出现意料之外的改动；
7. 容器反复重启，或出现内存不足被杀（OOM）。
