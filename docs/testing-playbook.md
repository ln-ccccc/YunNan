# 测试方法手册：技巧积累与采纳记录

本手册记录本项目沉淀下来的测试技巧、想不出测试思路时的检查单、以及对外部测试方法的采纳标准。它回答的是「**怎么想到这样测、为什么这样测是好的**」；选哪类测试、跑什么命令见 [开发规范第 6、7 节](development-standard.md#6-测试按风险选择)，两者不重复维护。

**为什么需要这份手册**：测试思路不是每次都能现场想出来。可靠的来源只有三种——本项目踩坑实录（最可信，附真实案例）、外部方法（必须过第三节的标准才能收）、以及两者的定期回顾。收录一切条目的共同底线：**说得出它比现有做法多抓住哪一类缺陷，并举出实例或写出可判定的验证实验，不凭"感觉有用"。**

每条技巧按固定格式记录：**解决什么问题 → 做法 → 为什么好 → 本项目实例（含日期）**。状态分三级：✅ 已验证（有本项目实测案例）、🧪 候选（写明验证实验，实验完成前不进规范）、❌ 已淘汰（保留淘汰理由，防止重复试错）。

---

## 一、已验证技巧

### 1. 递进测试：单文件 → 小批量 → 全量 ✅

**解决什么问题**：只跑单个用例或单文件时全绿，给人虚假信心；而环境、契约、多模块交互类问题只在更大范围暴露。

**做法**：按「单文件 → 相关模块小批量 → 全量 discover/全量套件」三级递进，每级通过才升级，失败就地定责后再继续。

**为什么好**：不同缺陷的爆炸半径不同——模块逻辑错在单文件暴露；fixture 路径、模块间契约在小批量暴露；环境配置、测试漂移、没人跑过的死角在全量暴露。三级各自覆盖一类，不可互相替代。且递进的成本极低：失败时范围越小，定位越快。

**本项目实例（2026-09-07）**：后端单文件 17/17 绿 → 小批量抓到「只挂 backend 漏了仓库根 tests/fixtures」的挂载错误 9 例 → 全量 299 例再抓出 7 个问题，其中 2 个是 `main` 上就存在的测试漂移，单文件和小批量都测不到。 miner 侧 13 → 12 → 60 全绿作对照。

### 2. 红灯验证：先证明测试能失败 ✅

**解决什么问题**：新写的测试可能永远通过（断言太弱、守卫没生效、测试对象接错），这样的测试是摆设。

**做法**：写完测试后，临时移除/还原被测的修复，确认测试**恰好失败在预期的那条上**，再恢复修复确认全绿。git stash 单文件即可完成，不动其他未提交内容。

**为什么好**：一个"修没修都绿"的测试给出的通过是噪声。红灯验证把「测试确实在被测行为上打钩」从感觉变成证据；且能验证失败信息本身可读（失败时打印的是不是人能看懂的原因）。

**本项目实例（2026-09-07）**：BFF `file_path` 守卫测试——stash 掉路由改动后恰好 12 过 1 挂（只有新测试红）；MapDashboard 生命周期测试——还原组件后 0 过 1 挂。两次红灯形态都符合预期才提交。

### 3. 安全守卫测试三件套：拒绝 + 上游计数为零 + 合法对照 ✅

**解决什么问题**：守卫测试常见两个漏洞——只断言了 422 却没发现请求仍被转发（副作用照常发生）；只测了拒绝，守卫写严了把合法请求也拦了却没人知道。

**做法**：一条测试同时断言：① 返回 422/400；② 用调用计数 fake 断言上游 client **调用次数为 0**（请求根本没出去）；③ 另配一条合法载荷的对照测试，断言放行且转发内容不被篡改。

**为什么好**：状态码只能证明 HTTP 层行为，计数为零才证明「拦截发生在这一层」；合法对照防过度拦截。三条合起来才构成守卫行为的完整定义。

**本项目实例（2026-09-07）**：`file_path` 守卫测试按项目负责人要求补了「未转发 Flask」断言（`createProjectDataset` 与 `request` 计数均为 0），并为 `storage_key` 合法登记加了转发不变对照。此前 `output_dir` 守卫测试（`projectRoutes.test.js`）已是这个形态，直接沿用了它的模式。

### 4. 生命周期泄漏：抽成配对纯函数再动态验证 ✅

**解决什么问题**：事件监听器、定时器、观察者这类「注册-注销」资源，写在组件里时单测框架够不到；泄漏（只注册不注销）在单测里永远发现不了。

**做法**：把注册/注销逻辑抽成 `createXxx` 纯 JS 工厂（返回 attach/detach 配对方法），组件只负责在挂载/卸载钩子里调用。测试用 stub 目标模拟 N 轮挂载/卸载循环，逐轮断言「挂载时恰 1 个监听、卸载后归零」，并验证事件送达恰一次、注销后不再送达。

**为什么好**：泄漏的本质是「注册与注销不配对」，只有动态模拟循环才能证明配对性；抽成纯函数后用仓库现有的零依赖 node:test 就能测，不需要引入 Vue 测试栈。成本极低（本次 12 行模块），且组件代码因此更简单。

**本项目实例（2026-09-07）**：MapDashboard 的匿名 resize 监听器泄漏 → 抽出 `createWindowResizeListener`，测试模拟 3 轮挂卸循环逐轮断言归零（`windowResizeListener.test.js`）。

### 5. 源码结构断言：锁 SFC 内的不变量 ✅

**解决什么问题**：Vue 单文件组件的内部写法在无组件测试依赖的环境里无法行为级测试，但某些约束（"禁止再做 X"）需要防止回归。

**做法**：按 `mapContainerLifecycle.test.js` 的既有模式，用正则对 `.vue` 源码断言结构（如"必须在 onUnmounted 里 detach"），配一条 `doesNotMatch` 禁止匿名注册。

**为什么好**：这是行为测试够不到时的降级手段，比没有强——它至少能保证「回归发生时测试会红」。但要清楚它的边界：只证明代码长这样，不证明行为正确。**与技巧 4 的分工**：逻辑能抽就抽出去行为级地测（优先），抽不出去的用结构断言锁约定。

**本项目实例（2026-09-07）**：`mapDashboardLifecycle.test.js` 三条断言与技巧 4 的动态测试互补：动态测试证明机制正确，结构断言证明组件确实在用这个机制。

### 6. 环境陷阱：失败聚类 → 最小复现 → 显式记录命令 ✅

**解决什么问题**：环境造成的批量误报（依赖缺失、资源路径、行尾格式）极易被误判为代码回归，浪费排查时间并消耗对测试的信任。

**做法**：三步——① **聚类**：大量失败共享同一错误家族（如全部是 CRS 相关）时优先怀疑环境；② **最小复现**：用一行代码验证假设（如 `ImportFromEPSG(4326)` 是否返回 0）而不是跑全量试错；③ **显式记录**：把能跑通的完整命令和陷阱签名写进文档，让下一个人不重踩。

**为什么好**：环境失败的特征是「同一根因、多处爆发、代码无关」。聚类+最小复现把几小时的试错压缩成几分钟的验证；记录命令把个人经验变成团队资产。

**本项目实例（2026-09-07）**：容器内 9 例 CRS 集体误报 → 一行 `ImportFromEPSG(4326)` 证实 PROJ 资源路径缺失 → 结论「必须先 conda activate」连同完整命令写入开发规范第 7 节。同日：CRLF 行尾（`file` 命令看到 `^M$`）导致的 2 例 bash 契约误报同理。

### 7. 被吞异常：在断言点取证 ✅

**解决什么问题**：代码里宽泛的 `except` 会把真实异常转换成另一个表面症状（如任务被标为 failed），测试报的错（`KeyError: 'result'`）不是根因。

**做法**：当失败断言读的是「调用参数」而代码里有宽泛 except 时，不要猜——在容器/本地复现同样的调用，把 mock 收到的实际参数打印出来（`call_args.kwargs`），被吞的异常通常就在 `error_message` 里。

**为什么好**：从表象（finish_job 没有 result 参数）到根因（`KeyError: 'classification_results'`）隔着一次异常转换；取证比顺着表象猜快得多，且证据是打印出来的实参，不是推断。

**本项目实例（2026-09-07）**：`test_inference_runner` 的 `KeyError: 'result'` → 容器内复现打印 `finish_job kwargs` → 得到 `error_message: 'classification_results'` → 定位到测试 mock 缺字段（见技巧 8）。

### 8. git 考古定责：代码漂了还是测试漂了 ✅

**解决什么问题**：测试失败后必须回答「是生产代码坏了还是测试过时了」，答案决定修哪边；猜错方向会把正确代码改坏。

**做法**：对涉事的代码文件和测试文件分别查最后修改的 commit 及其内容。若「代码新增了契约、测试停留在旧契约」，就是测试漂移——修测试；反之才是代码缺陷。

**为什么好**：几条 git log 就能把"疑似 bug"收敛成"测试漂移"，避免无谓的生产代码"修复"。这也是回归测试长期维护的核心动作：契约演化后测试要跟着长。

**本项目实例（2026-09-07）**：`inference_results.py` 最后改于 `72d5764`（新增 `classification_results` 返回字段），`test_inference_runner.py` 停留在基线 `e3c407f` → 判定测试漂移，生产代码正确。同日 `test_inference_image_contract` 对 `APP_IMAGE` 的旧期望值同类。

### 9. 数据限制：只读挂载资产做证明 ✅

**解决什么问题**："测试失败可能是因为缺权重/缺数据文件"如果不验证，就永远是不确定的猜测，测试基线立不起来。

**做法**：把缺失的运行资产从宿主机（main 工作区）**只读挂载**进容器，重跑失败用例。通过 → 证实纯数据限制，记入已知失败台账；仍失败 → 排除数据因素，继续查。

**为什么好**：把「大概是缺数据」变成实验结论。只读挂载满足项目「原始资产只读共享」的规则，不复制、不污染源工作区。

**本项目实例（2026-09-07）**：挂载 `backend/model/*.pth`（1.9G）与 `miner/yunnan.kml`（3.2M）后，`test_inference_runner` 与 `test_yunnan_project_seed` 各 1 例由错转绿，坐实数据限制分类。

### 9b. 容器内跑上传类测试：只读挂载与 Git Bash 路径转换陷阱 ✅

**解决什么问题**：上传/写盘类用例在「源码只读挂载」的容器里集体 `OSError: Read-only file system`，容易误判为代码回归；Git Bash 下 `docker run -w /app/...` 的容器路径被 MSYS 转成 Windows 路径直接启动失败。

**做法**：① 写盘依赖（上传目录等）在测试 `setUp` 里改指 `tempfile.mkdtemp()`，不依赖源码树可写；② 涉及 flask_uploads 的用例注意：`UploadSet` 的目标在 `configure_uploads` 时已定死，运行期改 `app.config["UPLOADED_PHOTOS_DEST"]` **无效**，必须替换 `app.upload_set_config["photos"] = UploadConfiguration(临时目录, None, IMAGES_WITH_TIFF, ())`；③ Git Bash 跑 docker 加 `MSYS_NO_PATHCONV=1` 前缀。确需写源码树内目录的历史用例（如探针文件落 `static/upload`），去掉挂载 `:ro`（该目录已在 .gitignore）。

**为什么好**：测试与挂载方式解耦后，同一份用例在本机与 CI 容器（无论 ro/rw）行为一致；陷阱条目避免下次重复踩 20 分钟。

**本项目实例（2026-09-19）**：`test_large_tiff_upload` 初跑 3 例 Errno 30，按①②改造后 `:ro` 挂载全绿；`test_security_recheck` 的探针用例属历史设计，rw 挂载跑过。

### 10. 黄金样例 fixture：固定 ID 与时间、整 JSON 比对 ✅

**解决什么问题**：断言逐字段手写容易漏字段、且随实现漂移；动态 ID/时间戳导致测试脆弱或诱导开发者"删掉动态字段再比"，比了寂寞。

**做法**：把接口的完整期望响应固化成 JSON 文件（固定项目 ID、固定时间或不含时间），测试里做**整 JSON 深比较**，不删任何动态字段。fixture 放仓库级共享目录，后端与 BFF 测试共用同一份。

**为什么好**：整 JSON 比对让「多返回了一个字段」这种契约变化立刻红；共用 fixture 保证 Flask 与 BFF 两层验的是同一个契约，契约变更必须改 fixture 才能过测试——这正是契约该有的严肃性。

**本项目实例**：`tests/fixtures/project-hub-v1/` 六个样例（blocked/partial/ready/assets 系列），`test_project_read_models.py` 17 例与 `projectRoutes.test.js` 透明代理测试共用；2026-09-07 全部解析与比对通过。

### 11. 连续运行验证：单次通过不算通过 ✅

**解决什么问题**：「执行一次」型的验证（推理、导入、导出、备份恢复）单次成功掩盖了状态清理与资源回收缺陷——临时目录、连接、句柄、模型/缓存的残留会污染第二次执行，线上表现为"每次启动只能跑一次，第二次必崩"。

**做法**（三级递进，源自江西 AGENTS.md §5.1，云南 2026-09-08 引入）：① **重复执行**——同一操作连续跑第二遍，第一遍验功能，第二遍验状态清理与资源回收；② **混合小批次**——抽样 ≥3 组不同形态输入串行执行，验证逐项隔离与累积效应；③ **全量回归**。三级通过才算该操作验证完成。

**为什么好**：第一遍和第二遍执行的代码路径通常相同，但进程状态不同；泄漏、残留、单例污染这类缺陷只会在第二遍及以后显形。让"再跑一遍"成为验收的硬性动作，成本极低，专抓一类极常见且单次验证永远抓不到的缺陷。

**本项目实例（2026-09-08）**：推理 worker 韧性移植（参考江西 EPIPE 事故「每次启动只能完成一次推理」）——容器内同一 worker 实例连续两次真实 CPU 推理（预载模型 + 真实流水线）均成功，进程内毒载荷/目录冲突混合序列回归测试锁定隔离行为；该事故类别从此有回归护栏。

### 12. 多视口布局扫描与渲染伪影甄别 ✅

**解决什么问题**：两类问题单靠"肉眼看页面"都难以定位——①布局在小视口/低分辨率下溢出或元素重叠；②页面本身没坏，但**渲染层出伪影**（整页内容平铺成多份、互相重叠、截图超时），两者症状看起来都是"界面乱了"，处理方向完全相反。

**做法**：
1. **DOM 优先定责**：先在页面上下文里做量化几何检测，不看截图——`document.documentElement.scrollWidth > innerWidth` 判水平溢出；对 `section/aside` 等面板两两算 `getBoundingClientRect()` 矩形相交面积（>8×8px 判重叠）；再查 `scrollWidth/transform/zoom/DevicePixelRatio` 异常。
2. **分级定责**：DOM 几何有问题 → CSS 断层，修样式；DOM 几何干净但截图/显示乱 → 渲染合成伪影，查 GPU 合成触发器（`backdrop-filter`、`filter`、`will-change`、大面积动画），逐个禁用对比截图。
3. **多视口扫描**：对 1366×768 / 1280×720 / 1024×640 三档逐视口重复检测，覆盖不同宿主环境。

**为什么好**：几何检测把"看起来乱了"变成可判定的数字（相交像素、溢出值），直接区分"修 CSS"还是"修渲染触发器"——本案（2026-09-09）程序化扫描证明布局三视口全绿，从而避免了一场无方向的 CSS 大改，精确定位到 3 处 `backdrop-filter`。
**本项目实例**：地图侧栏/顶栏的毛玻璃效果在 ZCode 内嵌浏览器触发整页平铺伪影（且伴随 dpr=0.9999 异常、截图超时），移除 backdrop-filter 后三视口扫描清零（`b3a5cdb`）。
**注意**：内嵌浏览器的截图功能本身可能超时或产出平铺伪影——**视觉验收以真实浏览器为准，自动化以几何检测为准**，不要用可疑截图反推 CSS 结论。


### 13. 滚动链审计：滚轮失灵与内容不可达 ✅

**解决什么问题**：页面内容比屏幕高，但滚轮怎么滚都没反应——下半部分功能（按钮、表单、列表）用户永远够不着。这类问题不会让测试失败、不报任何错，只有真人滚动时才会暴露。

**做法**：
1. **滚动链审计**（在页面上下文执行）：从光标处元素沿祖先向上走，逐层记录 `overflowY`、`scrollHeight` 与 `clientHeight`。Bug 特征签名：**内容比视口高（scrollHeight > clientHeight），但整条链上没有任何一层允许滚动**（全是 visible/hidden）——说明溢出内容被裁掉且无处滚动。
2. **修复后验证**：确认滚动链上出现可滚动层（`overflowY=auto/scroll` 且 `scrollHeight > clientHeight`）；程序化设置 `scrollTop` 后，目标元素 `getBoundingClientRect()` 应进入视口。
3. **注意验证手段的坑**：合成 `WheelEvent` 不会触发浏览器原生滚动（不可信事件的默认滚动行为不执行）——滚轮行为要么用真实输入模拟验证，要么以「滚动容器存在 + scrollTop 可驱使内容进视口」为判定依据；内嵌浏览器输入管线不稳时，程序化断言是可靠的验收口径。
4. **设计期预防**：凡 `height: 100vh` 的固定外壳，必须同时回答"内容比一屏高时从哪里滚"；配合全局 `body { overflow: hidden }` 时尤其危险——两层都堵死就是本案。

**为什么好**：滚动失灵零报错、零测试失败，肉眼不滚动就发现不了；滚动链审计把它变成 3 行可判定的数字（每层的 overflow/scrollHeight/clientHeight），30 秒定位，且能精确指出"该在哪一层补 overflow"。

**本项目实例（2026-09-09）**：项目工作台内容高 1897px、视口 768px，`body{overflow-y:hidden}` + 工作台外壳 `height:100vh` 无 overflow，用户滚轮失灵、下半页面板（资产/活动/导出）永远够不着。修复：仅给工作台外壳加 `overflow-y: auto`（`2739884`）；修复后滚动 600px 底部面板进入视口（scrollTop 可驱使），地图视图的满屏不滚布局不受影响。


### 14 后端全量回归的标准姿势（2026-09-20 审查定型）✅

**解决什么问题**：本机 conda 无一环境能跑后端测试（base 有 Flask 无 pytest、satellite-py310 有 pytest 无 Flask、geoview py3.7 且 conda.sh 指向失效路径），而"能跑"的容器里又埋着三个连环坑。

**标准命令**（主树全量回归，40 秒）：
```bash
MSYS_NO_PATHCONV=1 docker run --rm --entrypoint sh \
  -e PROJ_LIB=/opt/conda/envs/MMSeg310/share/proj \
  -e GDAL_DATA=/opt/conda/envs/MMSeg310/share/gdal \
  -e PROJ_DATA=/opt/conda/envs/MMSeg310/share/proj \
  -v "D:\项目\YunNan:/app" yunnan-runtime:current \
  -c "cd /app/backend && pip install -q pytest 2>/dev/null; python -m pytest test_*.py -q --tb=line -p no:cacheprovider"
```

**三个坑（每个都实测踩过）**：
1. **运行容器挂的是 worktree**：yunnan-backend 等五个容器的 /app 源码挂载来自 `.worktrees/feat-project-hub-low-coupling-foundation`，`docker exec` 进去跑测的是旧分支代码，不代表 main。
2. **docker cp 主树进运行容器 = 双包崩溃**：容器里已有 /app/backend 的 applications 包，再 cp 一份到 /main-backend 会造出两个同名包，`pkgutil`/`get_root_path` 解析抛 `ValueError: PurePosixPath('/') has an empty name`，51 个测试 1.4 秒全崩。要么整容器只挂一份代码，要么别混。
3. **MSYS 路径改写制造假失败**：Git-Bash 下 `docker run -e VAR=/linux/path` 的参数会被静默改写成 `D:/Git/linux/path`——GDAL/PROJ 齐刷刷报 "Cannot find proj.db"，9 个测试假失败（与技巧 14 旧坑同源但更隐蔽：值在容器里看是 Windows 路径才露馅）。凡 `docker run -e`/`-v` 涉及 Linux 绝对路径，一律加 `MSYS_NO_PATHCONV=1`。
4. **镜像有 ENTRYPOINT**：`docker run image sh -c ...` 的 sh 会变成 entrypoint 的参数（报 `sleep: invalid option -- 'c'`），必须 `--entrypoint sh`。

**判定基线**：当前 main 全绿口径 360 passed / 10 skipped / 149 subtests（pytest 9.1.1，容器内装）。

### 15. open-code-review 委托模式做全量审查（2026-09-20）✅

**解决什么问题**：要对 4 万行陌生/半陌生代码做甲方验收级审查，纯人读既慢又漏。

**做法**：
1. `npm i -g @alibaba-group/open-code-review`，用 **delegate 模式**（无需 LLM 配置）：`ocr delegate rule <files>` 按语言组输出系统规则（Python 详规/JS 详规/默认五轴），`ocr delegate preview` 看文件筛选。

3. **反思环节**（OCR 评论反思模块思想）：汇总后逐条亲自读代码复核再动手——本轮 7 包产出 ~70 条，复核砍掉误报、确认两包独立收敛同一 P1（60MB vs 8GB）后才修。
4. 修复回归后按 severity 汇报，快照沉淀在 docs/code-review/。

**为什么好**：规则来自实战检验的确定性管线而非即兴发挥；分包并行把 4 万行压到 40 分钟出全部 findings；强制证据格式让误报在复核环节现形。

**本项目实例（2026-09-20）**：docs/code-review/20260920-audit.md——7 包 70+ 条 findings，P1×9 当晚全部修复，后端 353→360 全绿、miner 47→48、双前端构建绿。

### 16. GUI 实跑巡检：后台标签会制造"伪缺陷"（2026-09-20）✅

**解决什么问题**：用内嵌浏览器自动化巡检 GUI 时，若标签页处于 `visibility: hidden`（宿主窗口未聚焦/面板未激活），会稳定复现两类**假 bug**：① 键盘/点击事件不路由（按 Enter 不提交表单、Playwright click 全部 actionability 超时）；② Vue `<transition>` 状态机卡死（`fade-enter-from` 永不移除，弹窗点 × 视觉上关不掉）——根因是 rAF 冻结，切回前台后自愈。

**做法**：
1. 巡检前先断言 `document.visibilityState === 'visible'`，hidden 时的交互类结论一律不作数。
2. hidden 环境下改用 **DOM 注入**（`element.click()` / `dispatchEvent` + `performance.getEntriesByType('resource')` 对账网络请求）验证数据流；视觉/过渡结论留给前台。
3. 用 `window.__errors` 收集器（error + unhandledrejection）全程伴随巡检，零 JS 错误是硬门槛。
4. `:refs` 依赖的初始化要警惕 `v-if` 门控时序——**GUI 实跑抓到的真 P1**：分类成果编辑器在 `loading=true`（骨架屏门控）期间调 `initializeMap()`，`$refs.mapContainer` 不存在而静默早退，地图永不渲染；修复=初始化移到 `loading=false` 之后的 nextTick，并加源码顺序守护测试。

**为什么好**：伪缺陷会消耗信任与排查时间（先查环境再定性，砍掉两例）；而纯单测/构建永远抓不到"refs 时序"这类只有真实组件挂载才暴露的缺陷——GUI 实跑是最后一道验收门。

### 17. element-plus@2.1.10 常驻通知的 close() 会静默失效（2026-09-22）✅

**解决什么问题**：函数式 `ElNotification({duration:0})` 返回句柄的 `close()` 实测不生效——上传进度/推理进度两个常驻通知在流程结束后**滞留屏幕**（GUI 实测 6 秒后仍在 top:16 全尺寸）。根因：句柄 close 写 `vm.component.proxy.visible = false`，该写入路径在当前 Vue 版本组合下到不了组件内部的 ref。

**做法**：
1. 自建 `utils/persistentNotification.js` 包装：创建后用"创建前后 `.el-notification` 集合差集"锁定本次 DOM 节点；close 时三级兜底——`句柄.close()` → 节点 `__vueParentComponent.exposed.close()`（走组件自身状态机与销毁记账）→ 直接 `removeChild`。
2. 判定"通知滞留"别用 `offsetParent`（fixed 定位元素恒为 null，会误报"已关闭"），用 `getBoundingClientRect().width` + `isConnected`。

**为什么好**：这类失效零报错、单测全绿（通知是 DOM 副作用），只有真实浏览器巡检"流程结束后查通知区"才抓得到；包装层一次修复覆盖所有常驻通知场景（上传进度、推理进度、后续任何 duration:0）。

### 18. GUI 文件上传注入：同源字节 + DataTransfer，当心 build 清 dist（2026-09-22）✅

**解决什么问题**：IAB 不支持原生 file chooser，真实上传流程无法用"点选择文件"驱动；而伪造 File（零字节/随机字节）会被后端栅格库拒读，测不到完整链路。

**做法**：
1. 把真实 tif 临时放进 `frontend/dist/`（容器静态服务目录，同源无 CORS 问题），页面内 `fetch('/__e2e_tmp.tif')` → `new File([blob],name)` → `DataTransfer` → `input.files = dt.files` → `dispatchEvent(new Event('change',{bubbles:true}))`。
2. `handleFileSelect` 会复位 `input.value`，注入后回读 `files.length===0` 是**正常现象**，以 UI 出现"已选择 N 个"为准确认。
3. **坑**：`npm run build` 会清空 dist——每次重建后必须重新投放临时文件，否则 fetch 拿到的是 SPA 回退的 index.html 字节（HTTP 200、字节是 HTML），假 tif 流进后端在 rasterio 处爆 500，极易误判成后端 bug。注入前先 `blob.size` 对账。
4. 测项目态路由需要带 `?project_id=N` 且影像空间匹配项目矿山（可用 DB 里历史 job 的 request_payload 找现成样本）；无项目上下文走 standalone 同步通道，不会建 job。

**为什么好**：让"上传→推理→取消→历史"全链路在真实栈可复现，取消闭环这类跨前后端的状态机只有端到端才能验证。

### 19. 改后端源码 ≠ 运行栈生效：挂载与内存模块的两层真相（2026-09-22）✅

**解决什么问题**：主树代码虽目录挂载进容器，但 gunicorn worker 进程加载的是**启动时**的模块——改完 .py 不重启，接口行为不变，而 traceback 会用**磁盘新源码**对旧行号，出现"traceback 里源码行与函数逻辑对不上"的诡异现象（本次 `_KML_ROI_PUBLIC_FIELDS` 常量行出现在 `kml_roi_inference_api` 帧里，正是新源码+旧字节码的信号）。

**做法**：
1. 判断运行栈是否已载入新代码：看 traceback 帧的源码行是否与函数名匹配；或 `docker exec <c> sh -c "grep -n <新标记> /app/.../file.py"` 确认磁盘是新、行为是旧 → 需重启。
2. GUI 验证后端改动前先确认这一点；不重启就用容器一次性 pytest（每次新进程，必然跑新代码）作权威验证。
3. 宿主机端口全断（curl 000）但 `docker ps` healthy 时，用 `docker exec <c> wget -q -O- http://127.0.0.1:<port>/` 验证容器内服务——区分"Docker Desktop 端口代理假死"（环境故障）与"服务真死"（回归），避免误停用户运行栈。

**为什么好**：把"改了但没生效"和"环境假死"两类排障各收敛成一个 30 秒可判定的检查，避免对着旧行为调试新代码。

### 20. Windows 测试工具链三坑：GBK 控制台 JSON / dd skip 单位 / 双 /tmp（2026-09-22）✅

**解决什么问题**：分片上传 E2E 首两次"后端行为诡异"（keepRawTiff 传了 true 却不生效、上传产物被删）——排查半小时发现全是**测试工具自身**的问题，被测代码从头到尾是对的。

**坑与判定法**：
1. **git-bash GBK 控制台的 `curl -d '中文JSON'` 按 GBK 字节发**：Flask `get_json(silent=True)` 静默失败回退空字典，所有开关落默认值——表象是"参数不生效"而非报错。判定：响应里该字段驱动的行为全按默认走；控制台回显乱码（鍒嗗潡...）即中招。规避：JSON 体用 python 以 UTF-8 写文件再 `curl --data-binary @file`。
2. **`dd bs=N skip=M` 的 skip 以 bs 为单位**：`dd bs=670726 skip=1` 取的是 [670726,1341452) 而不是第二块——服务端尺寸校验恰好通过（字节数对）但内容错位，组装出损坏文件走错分支。规避：切分块统一用 python `buf[off:off+n]` 或 `tail -c +N | head -c M`。
3. **Windows Python 与 git-bash 的 `/tmp` 不是同一个地方**：python 写 `/tmp/x` 落到 cwd 盘的 `	mp\`，curl/dd 读 `/tmp/x` 走 git-bash 挂载——`--data-binary @/tmp/x` 报 exit 26。规避：跨工具传文件用仓库内相对路径。

**为什么好**：三个坑都会制造"代码像是错了"的假象（尤其 1 的静默回退），各自 10 秒可判定；先排除工具链再查代码，避免对着正确代码调"bug"。

## 二、想不出测试思路时的检查单

按顺序过一遍，每条给出「提示自己」的问题和本项目实例。多数卡壳是忘了其中两三条。

1. **输入空间划分**：合法输入的边界在哪（空、零、超长、小数、Unicode、Windows 盘符、`..`）？非法输入的每个等价类各挑一个代表了吗？——例：`storage_key` 校验测了 `..`、`D:/`、绝对路径、大小写后缀。
2. **反向与未发生**：除了"该发生的发生了"，"不该发生的没发生"验证了吗（上游调用计数为零、无副作用、无多余字段输出）？——例：守卫三件套（技巧 3）、资产响应不含物理路径键的递归断言。
3. **状态机**：对象有哪些状态？每个转移触发了吗？**终态之后的行为**（终态任务不再当进行中）和**非法转移**（重跑同年、重复 FID）测了吗？——例：`vector_status` 转移、空间任务终态回退向导。
4. **竞争与时序**：两个请求交错、旧响应晚到、轮询期间切换对象，最新选择还能赢吗？——例：`createSelectionGate` revision token。
5. **故障注入**：依赖抛错、返回缺字段、返回错误码、超时、OOM 时，行为是可控失败还是崩溃/静默错？——例：publisher mock 缺字段暴露的契约问题（技巧 7）、GPU 失败回退 CPU。
6. **资源生命周期**：注册的东西注销了吗？反复进出 N 轮还平衡吗？——例：resize 监听（技巧 4）。
7. **失败不留半份成果**：中途失败后，磁盘上有没有残留的半成品？重试会不会叠加脏数据？——例：导出失败清目录、发布失败回滚备份。
8. **兼容与回归**：旧字段/旧接口形状还在吗？修 bug 前先写一个在旧代码上失败的新用例了吗？——例：红灯先行（技巧 2）、旧 `status` 与 `lifecycle_status` 并存断言。
9. **换一层验证**：单元过了，BFF 层转发还是原样吗？fixture 两层共用吗？全量套件里它还绿吗？——例：递进测试（技巧 1）。
10. **fixture 可达性**：fixture 造出的状态，生产流程真的能产生吗？给 retained 底图手工写 `.active`——恰是生产激活流程必删的标记，测试全绿但真实回退链路是死的。——例：2026-11-14 底图重激活（技巧 27）。

## 三、外部方法的采纳标准与候选区

**采纳四标准（全部满足才从候选升为已验证）**：

1. **缺陷类别明确**：能说出它比现有方法多抓哪一类缺陷，抓不到已知缺陷类别的不收。
2. **可落地**：在本项目工具链上可行，新增依赖、运行时间、维护成本列得清楚。
3. **验证实验可判定**：写明「引入后若能抓到 X / 证明 Y 则采纳，否则淘汰」，实验做完留结论。
4. **来源可信**：官方文档、实证研究或本项目实测优先；转述口碑需注明。

### 🧪 property-based testing（Hypothesis）

**它多抓什么**：人写示例测试靠枚举，等价类想漏就漏；property-based 生成成千上万输入（自动包含空串、NaN、Unicode 等刁钻值）并**把失败输入收缩成最小复现**，本质是"搜索我们误解代码的方式"（[官方文档](https://hypothesis.readthedocs.io/)；Anthropic 用它抓到过 numpy 真 bug 的[实验记录](https://www.anthropic.com/research/property-based-testing)）。

**验证实验**：对 `isSafeIncomingTiffStorageKey` / `_validate_incoming_tiff_storage_key` 这类路径校验函数跑一轮 property（"任何不在 `incoming/*.tif` 白名单内的输入必须被拒"）。找到绕过样本 → 采纳；一轮无增益 → 记"未增益"留档。**成本**：测试环境新增一个 dev 依赖。

### 🧪 mutation testing（mutmut）

**它多抓什么**：红灯验证（技巧 2）一次只能人工验证一个改动；mutation testing 把这件事自动化——算法改写源码（`==`→`!=`、删返回值等）生成"变异体"，**变异体存活 = 断言缺口**，直接量化测试强度（[官方文档](https://mutmut.readthedocs.io/)；其度量的是测试质量而非代码质量，见 [Codecov 实操文](https://about.codecov.io/blog/getting-started-with-mutation-testing-in-python-with-mutmut/)；学术对比见 [ACM 2024 四工具评测](https://dl.acm.org/doi/10.1145/3701625.3701659)）。

**验证实验**：挑断言密集的 `readiness.py` 或 `assets.py` 跑一轮，人工核对存活变异体是否对应真实断言缺口。缺口发现率高 → 采纳为季度性检查；存活解读成本过高/误报多 → 淘汰。**成本**：运行时间长（每个变异体跑一次测试），不适合进日常循环。

### 🧪 coverage 作缺口探测器（非指标）

**为什么这么定位**：覆盖率 100% 的测试可以全是无断言的摆设，把覆盖率当 KPI 会诱导写垃圾测试；但反过来，**分支覆盖数据能直接指出"从来没测过的路径"**（尤其错误分支），作探测器无害且便宜。**验证实验**：后端跑一次分支覆盖，人工核对未覆盖分支是否真为死代码/低风险；若能定位出遗漏的真实分支则保留为排查工具。**成本**：仅需 coverage 依赖，一次性运行。

### ❌ 已淘汰（保留理由防止重复试错）

- **Pact 类独立契约测试框架**：本项目前后端同仓、已有共享黄金 fixture（技巧 10），框架带来的 broker/多语言设施远超单人团队收益，违背 AGENTS.md「不为未来假设增加抽象层」。
- **浏览器像素级快照测试**：维护成本高、对无关渲染抖动过敏；UI 验收由人工浏览器走查 + 组件结构断言覆盖，快照与 fixture 职责重复。

### 21. Vue 组件挂载即崩的 DOM 形态与双通道视觉验证（2026-09-22）✅

**解决什么问题**：地图页"数据概览/分析统计两栏贴到一块"——DOM 审计两轮都报"零问题"，用户截图实锤打脸。真根因：MapContainer 的 defineExpose 置于被暴露函数 const 声明之前，setup 期对象字面量立即求值抛 TDZ ReferenceError，Vue 跳过该组件留下孤立 `<!---->`，地图区塌缩、右栏左移贴合、右侧留白。

**做法**：
1. **识别形态**：v-if/v-else 两个分支都不在 DOM + 容器里多出孤立 `<!---->` = 组件 setup 抛错被 Vue 吞掉（生产构建无 errorHandler 时不打断兄弟节点渲染，页面"看起来基本正常"）。DOM 审计要专门覆盖这种"应有组件缺失"形态，别只查重叠/溢出。
2. **console 捕获不能跨 reload**：先装收集器再 `tab.reload()` 会随文档销毁丢失（读到空数组假象"零错误"）。改用 **hash 路由切换**（`location.hash = '#/projects'` → `'#/map/1'`）触发组件重挂载，捕获器存活，TDZ 错误当场现形。
3. **emitImage 只回 CDN URL 时**，把 URL 直接交给 4.5v 视觉模型（analyze_image）做复核——几何数据（getBoundingClientRect 三栏宽度和 x 坐标连续性）+ 视觉分析双通道，两边都过才算验证。"我没看到画面"就不许下"零问题"结论。
4. **IAB 未聚焦时 CSS transition 冻结**：class 已切（`side-nav collapsed`）但 computed width 停在起点 200px——是 rAF 冻结的伪缺陷（技巧 16 同源）。判定：注入 `transition:none` 强制同步布局，宽度立即变 56px 即为环境特性而非产品 bug。
5. **改前端源码 ≠ 容器供新包**：miner-web 的 start 脚本每次容器启动现场 npm build（挂载 src），**docker restart 即换包**；排查"改了没生效"先 curl index.html 对比资源 hash 与磁盘构建产物是否一致。

**为什么好**：组件级挂载失败既不白屏也不报错到用户，单测测不到（需真实挂载）、纯 DOM 断言测不全（要看"缺了什么"）；本条把发现→定性→验证收敛成一套 5 分钟流程，并堵住"未看画面就宣称通过"的验收漏洞。

### 22. ZCode IAB evaluate 的表达式语义与深色宿主排查（2026-09-25）✅

**解决什么问题**：两个独立坑——① IAB `playwright.evaluate` 把字符串当**表达式**求值：传 `"() => { ...; return res; }"` 会拿到函数对象本身，序列化成 `{}`（假象：页面状态全空）；同一代码包一层 IIFE `(() => {...})()` 就正常。多行脚本静默变空对象，极易误判为"页面没渲染"。② 一次全页走查中 5 个页面在宿主系统深色模式下集体变黑（`body` computed `#181818`），但项目页/占位页正常——症状像"某页样式坏了"，实际是全局 `base.css` 保留了 Vue 脚手架的 `prefers-color-scheme: dark` 块，只有透明根节点的视图透出黑底。

**做法**：
1. evaluate 一律传 IIFE 或纯表达式，不传函数声明字符串；返回 `{}` 且无报错时先怀疑求值语义再怀疑页面。
2. 宿主相关样式问题先读 computed 值定责（`getComputedStyle(document.body).backgroundColor`），再全仓 grep 精确色值反查来源（`#181818` 一查即中脚手架变量），最后以「截图视觉 + computed 值」双通道确认，与技巧 12 的"DOM 优先定责"同构。
3. 浅色主题应用的两层防线：移除 `prefers-color-scheme` 块（守卫测试断言源码不含该串）+ 显式 `color-scheme: light`（防 UA 原生控件深色回流），两处都来自同一实测案例。

**为什么好**：函数字符串变 `{}` 是纯工具坑，不记录则每次都会浪费一轮"页面是不是崩了"的排查；深色宿主这类"看环境脸色"的缺陷在开发机浅色模式下永远不现形，走查时一旦遇到，色值反查 5 分钟可定位到行。本项目实例：86f6991/1c8740a（5 页透黑 + 占位页 100vw 溢出同轮修复，守护测试红灯验证后转绿）。

### 23. v-show 保活视图的隐藏按钮陷阱（2026-09-25）✅

**解决什么问题**：主控台用 `v-show` 保活项目工作台（切页不丢状态），其内部按钮（导出/快照等）在切走后**仍留在 DOM 里**。自动化按文案取"第一个命中"点击时，会命中**隐藏视图里的同文案按钮**——实测给"错误的项目"创建了快照（可见页选项目 1，操作落在隐藏工作台的默认项目 4 上），且页面显示各自"正确"，极难排查。

**做法**：
1. 自动化点击一律按**可见性过滤**：`[...querySelectorAll('button')].find(b => b.textContent.trim() === text && b.offsetParent !== null)`，禁止取"第一个匹配"。
2. DOM 断言（行数/计数）按视图根作用域收窄（如 `.data-manager-view .sub-panel`），不能全文档数同名类。
3. 数据归属不依赖页面显示，直接查 DB/上游实锤（本项目实例：project_backup_record.project_id 定位错绑）。

**为什么好**：v-show 保活是主控台架构的既定选择，它让"文档里有但用户看不见"的可交互元素成为常态；幽灵按钮对真人无害（无命中区域），只咬自动化。本项目实例：数据管理页快照错绑项目 4（410c9d8 后的 GUI 验收中发现并排除）。

### 24. Playwright route 逆序匹配会悬空瓦片请求，卡死 MapLibre load（2026-10-31）✅

**解决什么问题**：冒烟脚本给编辑器 fixture 配了 `map_manifest`（合成瓦片 URL）后，地图 canvas 正常出现但
NavigationControl/Draw 控件 30 秒永不出现，极易误判为"地图初始化回归"；实际是脚本自身的问题。

**根因与做法**：Playwright 的 `context.route` 按**注册逆序**匹配（后注册者先命中）。若把瓦片 route 注册在前、
`**/api/**` 注册在后，瓦片请求会落入 api handler；handler 里一旦对不认识的分支裸 `return`（不 `fulfill`），
请求即永久挂起——MapLibre 的 `load` 事件等待首批瓦片，永远不触发，`map.on('load')` 里的 addControl/
MapboxDraw 全部不出现。**所有 /api/** 资源放进单一 route handler 内按 endpoint 分支处理**（瓦片分支同样要
fulfill），或在 handler 末尾兜底 fulfill/404，禁止裸 return。

### 26. 数值一致性审计法：DB 权威值 vs 界面值逐项对表（2026-11-01）✅

**解决什么问题**：功能多了以后，"界面显示的数值对不对"靠肉眼逐页看效率低且容易放过口径级错误；纯代码扫描又发现不了统计口径的错误（代码逻辑自洽但口径错）。

**做法**：
1. **拉权威值**：直接从数据库 SQL 聚合（注意口径——如"图斑数=每矿山同年最新成果的 feature_count 求和"而非全行求和，全行求和会把同年多 job 重复计数）；
2. **拉界面值**：curl 界面背后的接口（带登录 cookie），逐字段取数；
3. **逐项对表**：每个数值标注口径再比——数字相同但口径不同也算"一致"，数字碰巧接近但口径不同要标"巧合"；
4. **异常值倒查**：量级明显荒谬的数值（如修复面积 5.4e14 m²）直接从显示处倒查数据源公式——本例根因是像元面积公式恒按度换算，遇到 EPSG:3857 源影像被重复乘 111320²。

**本项目实例（2026-10-31）**：矿山/数据/图斑数全对；修复面积天文数字 → 定位 `_pixel_area_m2` 的 CRS 假设缺陷（修复 ed6e5fc）。**配合技巧 25 的 CRS 感知**使用——多来源影像入库后，一切像素面积类统计必须按 label 实际 CRS 分支。

### 27. fixture 可达性：测试造的状态，生产流程能否产生（2026-11-14）✅

**解决什么问题**：底图重激活功能在生产上完全不可用——正常激活新底图会删旧底图 `.active` 标记（`backend/applications/project_hub/spatial_worker.py:334-335`），而重激活接口要求 retained 底图必须有该标记（`backend/applications/project_hub/spatial_service.py:597-598`），报错还误导为"瓦片数据已被清理"。但 `backend/test_basemap_reactivate.py` 四个用例全绿，因为 fixture 的 `_add_basemap` 给 retained 底图无条件手写了 `.active`——一个生产流程必然已删除的状态。

**做法**：测试通过后追加一问——**这个 fixture 状态是怎么来的？生产流程能产生它吗？**
1. 找出 fixture 写入的每个状态标记/记录/文件，反查生产代码里它们的全部写入点；
2. 若生产写入点与 fixture 行为矛盾（生产的"下线"会删、fixture 却保留），该测试验证的是生产不可达场景，断言再对也不构成验收证据；
3. 修 fixture 为"经生产流程产生状态"（如真跑一次激活→被新底图替换→变 retained），再断言目标行为；此时红灯先行（技巧 2）。

**为什么好**：它堵住"测试全绿 → 验收通过"的最后一层假阳性——被测函数没错、断言也没错，错的是**前提状态不可达**；这只有把状态的生产者与消费者对账才能发现。检查单第 10 条即本条的一句话版；与 [code-review 方法论"操作链状态一致性审查"镜头](code-review/methodology.md) 配套。

### 28. 同一镜像 ≠ 同一测试环境：compose 注入变量制造"那边绿这边红"（2026-11-14）✅

**解决什么问题**：dc9f0ad 全量在 yunnan-backend（运行容器）3942 全绿，换一次性容器（**同一镜像** yunnan-runtime:current）挂主树式复跑却 2 例必挂（test_security_recheck 的 init_db 用例）。真根因：`init_db.py` 模块加载即读 `MYSQL_PASSWORD`（env→.flaskenv→''），运行容器被 compose 注入了该变量，`init_db()` 走完整链路抛 RuntimeError、断言通过；干净容器 PASSWORD='' 走"跳过初始化"分支直接 return，`assertRaises(RuntimeError)` 等不到异常。测试隐式依赖了**生产容器状态**而非自造前提。

**做法（2×2 矩阵 + 单变量注入）**：同代码怀疑环境差异时，跑 {原环境, 干净一次性容器} × {unittest, pytest} 四格，再对可疑分支注入单个 env（`docker run -e MYSQL_PASSWORD=x`）复跑——3 passed 即实锤。全程 ≤2 分钟。

**规避**：测试不得隐式依赖宿主容器 env——setUp 显式 `patch.object(module, "PASSWORD", "unit-test")` 或进程内 setenv；**全量回归的声明必须写明运行环境**（哪个容器、有无 compose env、运行器）——pytest 与 unittest 计数口径不同（本例 unittest 3942 vs pytest 3946 项+2250 subtests），运行容器内可能根本没装 pytest。

**为什么好**：把"宣称全绿但别处复现不了"的信任损耗收敛成 2 分钟可判定的检查，同时堵住"测试只在带生产 env 的容器里绿"的假验收。

### 29. 慢接口拆解探针：perf_counter 分段定位非 SQL 瓶颈（2026-11-22）✅

**解决什么问题**：主环境项目列表/概览/资产三接口 15 秒 BFF 超时 502，慢查询日志只指向 MySQL，但真正瓶颈有两处根本不在 SQL：成果表整行加载连带 MEDIUMTEXT 大字段（worker 直接 OOM 崩溃、连接空响应），以及生产存储 /project_storage 是宿主 D 盘 9p/drvfs 挂载、单次存在性 stat 实测 ~8ms、641 条数据集串行 5.2s。SQL 日志与接口耗时都对不出这笔账。

**做法**：写只读探针脚本（create_app + app_context，perf_counter 分段计时：各条 query / 文件 stat 循环 / 组装 / schema dump / json dumps），`MSYS_NO_PATHCONV=1 docker exec -i -w /app/backend <容器> /opt/conda/envs/MMSeg310/bin/python - < probe.py` 直接在生产容器跑，用真实数据量分解。瓶颈定位后按语义选修法：大字段 load_only/列裁剪，只读 stat 线程池并发（语义不变），最后用响应逐字节比对证明 DTO 契约未动。

**规避**：① 修行尾别信 Git Bash 管道信号——`grep -c $''` 会匹配所有行给出假计数，编辑器/工具翻转行尾会让 git diff 显示全文件变更，字节级判定用 `python -c` 读 blob（subprocess 二进制可靠）；② localhost 双监听（wslrelay.exe 占 127.0.0.1、com.docker.backend 占 0.0.0.0）都通向同一 WSL2 容器，不是环境分身，别误判打错栈。

**为什么好**：把"接口慢"从猜测变成 5 分钟内的分段实锤，避免只盯着 MySQL 优化却放过文件系统与序列化；逐字节响应比对让性能修复与契约变更互相证明。

### 30. WebGL 画布验证：IAB rAF 饿死假象 + 无头真 GPU 裁决法（2026-11-23）✅

**解决什么问题**：视觉验收 WebGIS（MapLibre）画布时，IAB 内嵌浏览器给出的"空白画布"可能是纯环境假象：标签页/面板被遮挡时 `visibilityState=visible` 但 **rAF 一帧不发**（实测 2.5s 0 帧）——MapLibre 全靠 rAF 绘帧，画布永远空白、'load' 事件可能不触发、控件缺失；而截图管道部分可用（DOM 内容新鲜）会加深"页面活着就是没画"的迷惑。曾据此把地图空白误判为"dist 构建回归"，浪费整轮排查。

**做法**：①先用页面探针判环境：`requestAnimationFrame` 1-2s 计帧，0 帧=测量环境失效，停止在 IAB 内下结论；②裁决用**本机 playwright-core + 真 GPU 无头 Chromium**（临时目录 `npm i playwright-core`，`executablePath` 指向 `~/AppData/Local/ms-playwright/chromium-*/chrome-win64/chrome.exe`，启动参数 `--use-gl=angle --use-angle=d3d11`；SwiftShader 软渲染也可能不画，别用它下结论）；③**画布区域独立颜色数 + top3 占比**做客观判据：丰富渲染 ≥数万色/top3<5%，空白 ≈90%+ 单色；④"这边好那边不好"的地图问题，先比对**数据地理覆盖**（成果 fitBounds 的矿山 vs 底图金字塔 bounds）再查代码。

**规避**：不要用 IAB 的画布截图给 WebGL 页面做验收结论；同 harness 对照（好/坏页面各跑一次无头）是分辨"环境假象 vs 真缺陷"的最快路径。

**为什么好**：把"画布空白"从主观截图判断变成三步可复现的判定链（rAF 探针→无头真 GPU→色彩统计），避免在错误归因上消耗整轮时间。

### 31. 提交前逐文件行尾扫描：编辑工具翻行尾 + git stat 缓存掩盖（2026-11-24）✅

**解决什么问题**：本仓库有 156 个文件处于"索引 LF、工作区 CRLF"，但 `git status` 显示未修改——index 缓存的是 CRLF 文件的 stat，内容差异被跳过。任何人或工具一编辑，mtime 变化后 git 重读内容，`git diff` 变成整文件翻转，真实改动被淹没。本轮里编辑工具对零散的 `.py/.vue/.js` 写出了 CRLF，每次落在不同文件上，靠肉眼无法预防。

**做法**：提交前跑字节级扫描（脚本 `normalize_eol.py` 的思路）：对每个变更文件比较 HEAD blob 与工作区的 `\r\n` 计数，并对比 `git diff --numstat` 与 `--ignore-cr-at-eol` 的行数，两者差距大即整文件翻转；HEAD 为纯 LF 而工作区为纯 CRLF 的文件按字节替换 `\r\n→\n`。读 blob 用 `subprocess` 二进制（见技巧 29）。不要用 `find` 扫全仓——生产存储挂在这棵树下，遍历要几分钟。

**为什么好**：把"diff 里全是噪声"变成提交前 10 秒的确定检查；顺带保证生产挂载树上的文件行尾与仓库一致。

### 32. 全绿但慢 N 倍：用 --durations 找"恰好等于某个超时值"的用例（2026-11-24）✅

**解决什么问题**：统计链集成测试 14 个用例跑了 304 秒却全绿。原因是测试里的补丁打在了函数定义方的命名空间，而被测模块是按名字直接导入（`from x import f`），补丁没生效——嵌套的保存再次申请本进程已持有的文件锁槽位，等到 300 秒超时后被被测代码里宽泛的 `except Exception` 吞掉，测试"碰巧"通过。

**做法**：批次耗时异常先 `pytest --durations=10`；单条耗时≈某个配置的超时上限（300/600/1200s）一律视为假绿，查它吞掉了什么；给"按名字导入的函数"打补丁要打在**消费者**的命名空间上；被测代码里的宽泛 `except` 要在测试里用调用次数/写入次数的断言逼出失败路径。另一条同类教训：集成用例第一步必须断言入口调用成功并带响应体——夹具里的 `feature_id` 没沿用基线 ID 时，保存直接 422，后续断言全在测错误分支。

**为什么好**：全绿但慢得离谱的批次里一定藏着被吞掉的失败；durations 是成本最低的探测器。

### 33. 地图浏览器脚本的四个静默失败点：浮层吞点击、画布焦点、重叠图斑、消息框淡入（2026-11-24）✅

**解决什么问题**：编辑器回归脚本的"合并"场景画不出面——工具退出、什么都没画出来、页面零报错。排查先怀疑"放弃编辑后键盘失灵"的产品问题，被对照实验否定，才回头逐次点击看落点。

**做法**：
1. **点击地图前断言落点**：`document.elementFromPoint(x, y)` 必须是画布。提示浮层、地图控件会吞掉落在它们下面的点击且没有任何反馈。本例是地图右下角的纯文字提示浮层（夹具没有底图时出现），顺带发现并修了一个产品缺陷（`pointer-events: none`）。

### 34. "偶发 502"不许留成偶发：失败响应对到具体请求，日志里取 cause（2026-11-24）✅

**解决什么问题**：真实浏览器验收里出现过一次 502，复跑两次没复现，差一点被记成"偶发"。实际是存在已久的线上缺陷：Miner BFF 随机 502（日志保留范围内 38 次，全是 `UND_ERR_SOCKET`）。

**做法**：
1. 验收脚本的每个失败响应都记 URL、状态、响应体、时刻；失败时转储在途与慢请求。带着没解释的错误不算通过。
2. **循环跑到复现**（本例 6 次里中 2 次），拿到具体接口；一次没复现不构成结论。
3. 去容器日志按错误串 grep 并取 cause（`TypeError: fetch failed` → `cause.code`）。`docker logs -t` 带时间戳，按小时 `uniq -c` 得到真实频率——"发生过多少次"用计数，不用印象。日志驱动不是 json-file 的容器 `docker logs` 可能是空的，先确认日志去哪了。
4. **根因实验贴着运行环境**：容器内 Node（18.20.3）≠ 宿主 Node（24）。用**原始 TCP** 写一个照服务端行为的模拟服务——Node 的 http server 会自动发 `Keep-Alive` 超时提示而 gunicorn 不发，用 http server 做实验会得出"无竞态"的假结论（本次第一版实验就是这样错的；另一处错是预热请求没读响应体，连接根本没被复用）。Git Bash 调 `docker exec` 要 `MSYS_NO_PATHCONV=1`，宿主路径写 Windows 形式。
5. 修复前后用**同一个脚本、同样的节奏**量：240 次 27 失败 → 720 次 0 失败；代价单独做微基准（每次上游请求多约 0.6ms），不靠估计。

**为什么好**：间歇性故障的修复证据不能是"后来没再见到"；"失败率对照 + 日志归零 + 代价微基准"让"偶发"变成可验收的结论。本项目实例：bc50f8c。

### 35. 修一个点之前先全量 grep 同类写法；规则只留一处 + 扫描守护 + 对旧版本报红（2026-11-24）✅

**解决什么问题**：回收审查判定"编辑器下载后立刻 revoke object URL"要修，改完才发现同一个写法还有 4 处（Miner 导出成果、快照清单、趋势 CSV，GeoView 图片下载）——其中导出成果下载正是导出链路的最后一环。只修被点名的那一处等于没修。同一轮里 BFF 的出站 `fetch` 也是 4 处、同吃一个竞态。

### 36. 提交时 git 报 `bad object header`：先证明仓库没坏，再继续（2026-11-24）✅

**解决什么问题**：一条命令里连续做两次提交，第二次提交的输出里夹着后台自动维护的报错：`error: bad object header` / `unable to get object info for <oid>` / `task 'gc' failed`。看起来像对象库损坏。

**做法**（全程只读，不跑 gc/prune）：
1. `git cat-file -t <oid>`、查松散目录、`git verify-pack -v <idx> | grep <oid>`、在 `.git` 里（除 objects/logs）grep 该 OID、`git rev-list --objects HEAD | grep`——确认它是否被任何引用、索引、工作树需要。本例：哪里都没有。
2. `git fsck --connectivity-only --no-dangling`：可达图是否完整（4 秒）。
3. 内容级校验只做今天动过的部分：新包 `git verify-pack`、今天的提交 `rev-list --objects A..HEAD` 逐个 `cat-file -e`、松散对象逐个 zlib 解压核对长度与 OID；检查没有残留的 `.lock`/`gc.pid`。
4. 对照时间线定性：`.git/objects/<xx>/` 的 mtime、最近写入的松散对象、`git log --all --since` 看是否有别的会话在别的 worktree 写对象（所有工作树共用一个对象库）。本例是上一个提交触发的后台自动维护与紧随其后的 `git add`/`commit` 并发，读到了正在落盘的对象。

**为什么好**：对象库报错时最坏的两个反应是忽视和贸然修复。四步检查两分钟内把"疑似损坏"变成"可达图完好、今天的对象逐一校验通过、原因是并发读写"，之后才能放心继续提交。规避：触发了自动维护（松散对象数过了 `gc.auto` 阈值）之后，下一条提交命令前稍等或先看 `git count-objects -v`。

### 42. 「等价替换」要验证到库的真实行为，版本不同 API 就不同（2026-11-24）✅

**解决什么问题**：照着对 Shapely 2.x 的印象写 1.8.5 的代码，连踩三个坑，每个都只在做冒烟时才暴露：`STRtree.nearest()` 在 1.8 返回几何对象、在 2.x 返回下标；`STRtree.query()` 返回的不保证是传入的同一个对象（按 `id()` 对回去会悄悄漏掉一半）；`PreparedGeometry` 在 1.8 没有 `distance`。前端那份手写的有效性检查的注释里写着「用 shapely 2.1.2 / GEOS 3.13.1 核对过」，而生产是 1.8.5 / GEOS 3.10.3。

**做法**：动手前先在**生产运行时同一个镜像**里跑一段十几行的探针，把要用到的每个 API 的返回类型打印出来（`repr` 和 `type`），再写正式代码。凡是注释或文档里声称「与某某版本核对过」的，核对一下那个版本是不是生产在跑的。

**为什么好**：探针只要一分钟；而这类差异不会报错，只会给出错误的结果。

### 43. 同一份代码给出不同答案：先确认底层库是不是确定的（2026-11-24）✅

**解决什么问题**：绑定同一个 commit 的两次回归，简化成功数差 1（137,041 对 137,042）。第一反应是自己哪里没钉住版本。实际原因是 GEOS 3.10.3 的拓扑保持简化对少数输入**依赖输入对象的内存地址**：同一个图斑，每次新建一个等价对象去调用，200 次里出现两种输出。

**做法**：
1. 用哈希给输出做指纹（`wkb.dumps` 后 sha256），同一个对象连算 N 次、每次新建对象再算 N 次，分别统计不同指纹的个数——两种做法结论不同，就说明依赖地址。
2. 在全量数据上量出比例（抽样 19,779 个图斑有 7 个；全量两两相乘有 23 / 144,176），而不是只确认「存在」。
3. 评估影响面：这里的两种输出都过校验（要么合法返回、要么拒绝保持原样），所以正确性不受影响，受影响的只是可复现性；把替代的确定性方案的数据一并列出来，交给负责人取舍。
4. 回归报告里写明「计数末位 ±N 来自此处」，并让回归脚本自己量这个数（`final_regression.py` 的 `geos_nondeterministic`）。

**为什么好**：把「数字对不上」从一笔糊涂账变成一个有名字、有比例、有兜底保证的已知事实。

### 44. 数请求次数不等于验证了行为：必须断言看得见的结果（2026-11-24）✅

**解决什么问题**：前端把校验接口返回的 `{ items }` 对象当成结论数组往下传，调度器发现不是数组就静默丢弃。结果是请求照发、后端照答「越界」，界面上一条提示都没有——而夹具测试断言了「至少发出 11 次校验请求」、源码守卫式的单测全是绿的。是真实数据测试里「画一个越界的面 → 等提示 → 没等到」抓出来的。

**做法**：
1. mock 接口的测试里，至少有一组让接口返回**不合法**的结论，并断言界面上对应的文案出现（截图留证）。
2. 「请求发出去了」只能作为辅助断言，不能作为这条功能的通过条件。
3. 把「响应数据 → 结论」的对接收口成一个纯函数（`matchVerdicts`）并单独做单测：返回结构不对、数量对不上时返回空，而不是把下标错位的提示弹出来。
4. 新功能在合并前，至少有一次在真实浏览器里走完「操作 → 等响应 → 看界面」的完整链路。

**为什么好**：这类缺陷的共同点是每一层单看都「做了自己那步」，只有端到端断言最终可见结果才能发现。

### 45. 验收结果绑定 commit：源码从 `git archive` 导出后只读挂载，改动代码就重跑（2026-11-24）✅

**解决什么问题**：一轮工作里回归跑了好几次，其中第一次用的是还带着缺陷的代码（后来才发现的缩进错误），另一次用的是改之前的 commit。如果直接拿这些数字写报告，就是「用旧构建的测试结果证明新代码正确」。

**做法**：
1. 运行器先 `git archive <commit> backend` 导出到仓库外目录，再把这个目录**只读**挂载进容器当作被测源码；工作区后来怎么改都不影响。
2. 每次运行把下列内容写进 `binding.txt`：commit 全称与时间、被测关键文件的 sha256、数据文件 sha256 与行数、Python / Shapely / GEOS / rasterio / numpy 版本、镜像 ID。
3. 报告里只引用绑定到最终 commit 的那次结果；之前的运行明确标为「已作废」并写出原因。
4. 做实验的脚本本身入库（`backend/tools/geometry_engine_experiments/`），并核对入库副本与实际运行的那份哈希一致。

**为什么好**：报告里的任何一个数字都能回答「哪个 commit、哪份数据、哪个版本的 GEOS」。发现底层库有不确定性时（技巧 43），也能说清楚末位差异的来源而不是含糊带过。

### 46. 不碰生产的隔离沙盒：临时库选择性复制 + 一次性后端 + 浏览器内改写入口（2026-11-24）✅

**解决什么问题**：要在真实影像、真实矿山边界、真实推理成果上验证编辑器的新流程，但不能重启生产容器、不能让新代码连生产库（后端启动时的建表 / 迁移逻辑会写库），生产库又有 3.6 GB 不便整库复制。

**做法**：
1. 起一个临时 MySQL（不发布端口），用 `mysqldump ... | mysql` **流式**复制：全部小表整表复制，三张大表只复制结构加沙盒项目的行（`--where=project_id=<沙盒>`），落盘为零。
2. 起一个一次性后端容器：挂载定稿 commit 的只读导出、连接临时库、宿主只发布 `127.0.0.1:<端口>`；存储目录照常挂载（写入只发生在沙盒项目自己的目录下），输出类的命名卷换成临时卷。
3. 前端用指定后端端口另行构建到仓库外，起一个本地静态预览。
4. 浏览器测试照常从 Miner 的真实入口进入，用 `context.route` 把 Miner 打开生产 GeoView 的请求在浏览器内 302 到预览——生产前端收不到任何请求。
5. 用完执行拆除脚本：删容器（含匿名卷）、临时卷、临时网络，以及那个含密钥的环境文件。

**踩过的三个坑**：
- `mysql` 镜像初始化时会先起一个只走本地套接字的临时实例，`mysqladmin ping` 那时就返回成功但 root 口令还没生效。就绪检查必须**用口令走 TCP 真正查一次**。
- `--where=result_id IN (SELECT ...)` 里的括号在 `sh -c` 里不加引号会被 shell 吃掉。而当时我把错误输出重定向掉了，脚本「静默成功」但修订表是空的。**复制类步骤不屏蔽错误输出，并核对行数**（成果数、修订数）。
- 口令放在命令行上会有 `Using a password` 告警干扰判断，改用容器内的 `MYSQL_PWD` 环境变量。

### 47. 上线前先在隔离栈里走一遍「发布 → 核对 → 回滚」，只换项目名挡不住写死的名字（2026-11-25）✅

**解决什么问题**：要验证"把一个固定提交放到生产上"的流程，但不能拿生产试。只给 compose 换一个项目名是不够的。

**做法**：
1. 渲染演练栈的完整配置，**起任何容器之前**逐项断言：容器名、命名卷名、网络名全部带演练前缀；发布的端口里没有生产端口且只绑 `127.0.0.1`；每一个绑定挂载只落在允许的目录里，没有任何可写挂载落在开发主树上；演练环境文件钉住的是候选发布目录。
2. 覆盖文件里必须逐项盖掉主文件里写死的三类东西：`container_name`（否则与生产容器重名）、命名卷的 `name`（否则直接挂上生产的 `yunnan_mysql_data`）、`ports`（compose 对端口是追加而不是替换，要 `!override`）。
3. 演练前后各给生产的每个容器拍一次快照（容器 ID、启动时间、重启次数、挂载），比对必须完全相同。
4. 清理用 `docker compose -p <演练项目> … down -v`，删之前先打印它管得到的卷名，确认全部带演练前缀。

**为什么好**：这次演练抓到六个问题，全部发生在动生产之前，其中"后端容器起不来"如果直接上生产，就是旧容器已删、新容器起不来。

**踩过的坑**：审查脚本自己也犯过与被审对象同类的错——路径的大小写与 `./` 没归一化、调用对账时没传环境文件。审查脚本报的红要先分清是脚本的问题还是配置的问题。

### 48. 「源码从开发树挂进去」的隐含依赖：未提交条目逐个归类，挂载点要预先留好（2026-11-25）✅

**解决什么问题**：容器挂的是整个开发树，树里没入库的东西也在被容器使用。换成只含一个提交的发布目录后，这些东西悄悄不见了——容器能起来，功能坏了。

**做法**：
1. 用 `git status --porcelain --ignored -- <发布路径>` 列出开发树里所有未提交的条目，逐个归类：运行时资产（入库则违反仓库规则的大文件与第三方源码）、挂载点、已知不进发布目录的东西。**出现归不了类的一律拒绝生成**，不靠人记得。
2. 这次的清单：推理权重两个（7.5 GB）、预训练骨干权重加随附的 `mmseg`、`dinov3` 源码目录、四个旧模型目录，共 10.16 GB；被 `.gitignore` 忽略的 `backend/.flaskenv` 里有一套库口令（生产不用它，compose 给的口令优先）。
3. compose 在只读的 `backend` 之上还挂了命名卷，挂载点目录在发布目录里必须预先存在——只读文件系统里建不了目录，容器直接起不来。发布目录里留空的挂载点，核对时检查它们仍然是空的。
4. 资产逐个记账（大小、文件数、SHA256）并在容器内核对。推理权重的 SHA256 与项目里原有的校验记录一致，等于免费多了一道交叉验证。

**为什么好**：把"靠碰巧带进去"变成"列出来、记下来、核对过"。下次有人往开发树里放一个运行时要用的文件，生成发布目录时就会被拦住，而不是上线后才发现。

### 49. 「等健康」的等待逻辑要用真实的延迟就绪容器去测（2026-11-25）✅

**解决什么问题**：切换脚本每一阶段都要等容器健康。演练里"75 秒完成四个阶段"是假象——后端根本没起好就进了下一阶段，GeoView 和 Miner 阶段完全没等。

**做法**：
1. 写一个几十毫秒级的小容器（`--health-cmd 'test -f /tmp/ready'`、探测 1 秒一次），按四条路径测等待函数：延迟就绪必须等够；中途"不健康"再恢复不算失败；第一个服务慢、第二个快，第一个不能被丢掉；容器退出立即报失败。
2. 把缺陷加回去跑一遍，四条必须全部报红。
3. 等待期间读状态时，待定项的内容是"服务名=状态"，匹配模式要对着这个完整字符串写。

**踩过的坑**：等待函数开头多写了一句 `shift`（超时是全局变量，没有位置参数要跳过），把每阶段的第一个服务名丢掉了。GeoView 冷构建要四五分钟，健康探测连败五次后状态会变成"不健康"、构建完再恢复——容器只要还在运行就该继续等，退出、重启循环、不见了才算失败。

### 50. 被杀之后先找真正的热点，不带错误归因往下走（2026-11-25）✅

**解决什么问题**：一个对照计算连续三次被内存上限杀掉（退出码 137），前两次的归因是"进程开多了"，改成单进程照样被杀。

**做法**：
1. 先看是哪一层的内存事件：`docker events` 里只有自己那个一次性容器有 `oom`，生产的容器没有事件、运行时长连续——影响范围确定了。单进程加硬上限重跑，被杀的只会是它自己。
2. 数据本身很小（最大一条成果 2 万个坐标），热点不在计算上，在入口：脚本把 3029 条成果一次性全部解析成 Python 对象再分给子进程，约 2200 万个坐标，光对象开销就约 2.6 GB。
3. 改成流式——逐行读、在子进程里解析——之后 15 分钟跑完，没有任何问题。同一份数据的定稿回归脚本本来就是流式的，峰值只有 113 MB，差别只在这一处。

**为什么好**：同样被杀的三次，原因与前两次的说法都不一样。下次遇到"改了 X 还是被杀"，先怀疑归因，用数字（单条数据多大、对象开销多少、哪一层的事件）把原因钉死。

### 51. 浏览器脚本点不中、数不对：先量清楚再改断言（2026-11-25）✅

**解决什么问题**：真实浏览器冒烟里连续几轮"多选到 3 个面、请求里却是 4 个""点了目标面却什么都没选中""合并按钮是灰的"。

**做法**：
1. **屏幕坐标在点击前一刻重算。** 校验状态条出现时画布上移几像素，画布获得焦点时页面可能滚动一百像素；提前算好的坐标到点击时已经不准。
2. **读数与事实对不上时，把过程记下来**：每次点击想要的面与点击后的选中数、请求体里各个几何的顶点数。这次记录显示实际点了五下、第一下没点中、其余四下生效——请求里的 4 个面是对的。
3. **事件的时间基准要搞清先后**：绘制库的选中变化事件先于地图的点击事件发出，按"距上一次点击的毫秒数"去记，每次都正好等于我两次点击的间隔，看着像是"每次都晚一秒"，其实选中是即时的。
4. **最小复现排除了产品问题**：单击、按住 Shift 连点三下，选中都稳定不变；"之后自己多选了一个"没有重现，就不作为缺陷登记，如实写成未重现的观察。
5. **合并选不中面，是落点规则**：新画的面盖住了落点，命中的是更小的那个面；产品点择时"顶点择近"优先。合并场景改成选不贴边的目标面——贴边的面与别的面取并集会超出矿权范围被门槛拦下，那是产品的既定行为，不是合并失败。
6. **选中可以用绘制库自己的接口完成**（选中不是编辑动作），然后照旧点真实的按钮；点选的命中规则另有专门的夹具覆盖。

**为什么好**：六个"失败"里五个是脚本自己的问题，一个是产品在正确地拒绝。把每一个都量清楚，才分得清哪些该修脚本、哪些该记成产品的既定行为。

### 52. 旧页面兼容性：用改过端口的副本，别让旧页面连到生产后端（2026-11-25）✅

**解决什么问题**：上线当刻用户已经打开的旧页面遇到新后端会怎样，回滚当刻已打开的新页面遇到旧后端会怎样。要在隔离栈上测，但旧构建的产物里写的后端地址是生产的端口。

**做法**：
1. 先查旧产物里后端地址是怎么拼的。GeoView 是构建时按"页面自己的协议和主机名 + 固定端口"拼的，所以把现网产物拷一份副本，只把 `port:"5008"` 改成演练端口，用仓库里的静态服务脚本挂到演练网络上。原产物不动。
2. 新构建的副本从演练的前端容器里 `docker cp` 出来，它的地址本来就是演练端口。
3. 后端的跨域白名单只认自己的端口，兼容测试用的端口要显式放行；一旦显式配置，GeoView 自己的端口也要写进去。先用 `curl` 发一个带 `content-type` 的 POST 预检确认，再上浏览器。
4. 四格都跑一遍：生产现网页面 × 新后端、新页面 × 回滚目标后端、回滚目标页面 × 回滚目标后端、新 × 新。
5. 回滚目标是什么要查实，不要想当然：这次的回滚基线也带几何接口（是上一轮的引擎），不是"没有引擎"。

**踩过的坑**：两个构建的组件字段不一样——旧构建里没有"忙"标志，等它变回 `false` 会等到超时。等待条件写成"不是在忙"，并且先等一小会儿再判断。

### 53. 造数脚本只依赖生产环境里有的库，参数按真实数据的分布定（2026-11-25）✅

**解决什么问题**：隔离栈不带推理 worker，需要用真实的发布函数把构造的 label 发布成成果。造数脚本连着错了七八次才跑通。

**做法**：
1. 在演练的后端容器里运行，只用那里有的库。生产镜像里没有 pyproj，坐标变换改用 rasterio 自带的 GDAL / PROJ。写之前先 `import` 探一下。
2. 筛选条件先看数据的真实分布：这批矿山面积的**中位数只有约 6600 m²**，最大的一座 0.28 km²，按"几平方公里"设的区间一个都选不中。
3. 窗口边长是米、像元步长在经纬度坐标系下是度，像元个数要按米算。
4. 斑块围绕某个点用局部坐标画，画完要平移回真实位置。
5. 同一座矿山同一年份的后一条成果会取代前一条（`effective=false`），被取代的成果不适合做编辑测试——两条成果用不同年份。

**为什么好**：这些错每一个都只需要几秒钟就能改掉，但如果不在容器里直接跑、只在脑子里过，是发现不了的。

### 54. 改完先确认"真的改了"，再跑长流程；说明文字写在事实后面（2026-11-25）✅

**解决什么问题**：这一次里反复出现"打了补丁、跑了四五分钟、结果和上次一模一样"——补丁脚本在某一处多行文本上没匹配到，断言失败，文件根本没写入；或者编辑工具报了"没找到"却照样往下跑。还有一次提交说明里写了"再切回候选各一次"，而那件事当时还没做。

**做法**：
1. 改完立刻用一个便宜的检查确认改动生效（`grep` 新字符串的出现次数、`node --check`、自测），再去跑耗时的那一步。
2. 多处的修改不要用"一个脚本叠一层补丁"的方式做第三次、第四次；直接读出当前内容，用编辑工具逐处改。
3. 多行文本做匹配锚点时缩进和转义最容易对不上；用短的、单行的、一定唯一的锚点，并把匹配失败当成错误而不是跳过。
4. 提交说明、报告里的每一句"已验证"，都要对应一件已经发生的事；还没做的写成"待做，结果见某处"。发现写了超前的话，提交没推送之前直接修正。
5. 在终端里看中文输出不要用按字节截断的命令（`cut -c`、按字节数 `head -c`），会把多字节字符截开，整段输出被按错误的编码显示，看着像乱码而实际文件是好的。

**为什么好**：这一条不涉及任何技术难点，却是这次浪费时间和上下文最多的地方。

### 55. 失败安全要逐条「把失败造出来」验证，并盯着配置文件的字节（2026-11-25）✅

**解决什么问题**：切换脚本此前只在顺利路径上跑过三次。发布前复查查出四处只在失败时才暴露的缺陷：状态值多包了一层引号，`--rollback` 永远判不成「上一次成功」；ERR 兜底没加 `set -E`，在函数里根本不触发；首次切换失败后给出的恢复提示与实际行为不一致；状态文件按发布根共用，演练留下的记录会让生产回错版本。工具的单测直接调 Python 函数，这些一处都测不到。

**做法**：
1. 把「可能出错的每一步」列出来，逐个造真实的失败：对账失败（给一个不存在的 config 覆盖）、写配置失败（把环境文件设成只读）、任务在跑（用栈启动时自动建的真实任务，不造数据）、钉住之后阶段失败（`--timeout 15`）、写失败之后再 `--rollback`、成功之后 `--rollback`、再切回。
2. 每一步固定记录四样东西：环境文件的 SHA256、钉住的版本、状态文件、容器列表——先记再比，不靠读日志的印象。
3. 驱动脚本「执行 → 记录 → 与预期逐项比较，不符即停」，一步一个日志文件；修了脚本就从这一步重跑。
4. 写 shell 之前用十行的小实验确认语义：ERR 陷阱进不进函数（要 `set -E`）、`$(...)` 里的失败会不会打印两遍、`timeout` 能不能杀住原生的 docker（退出码 124）。
5. 特有参数要排在公共参数之后（同名选项后者生效），否则注入的失败根本没生效，测试却以为验过了。

**为什么好**：这些缺陷没有一个会出现在顺利路径上。逐条造过失败之后，「写配置之前什么都不动」从设计意图变成了每次都验证的事实；测试过程中还顺带发现了两个真实的健壮性问题（新库配旧存储，后端启动迁移崩一次；全新栈首次启动时切片 worker 复制底图不刷心跳，健康检查判它不健康，一次成功的切换被收尾核对判成失败）。后一个说明：核对的「不符合预期」要先分清是被测对象的问题，还是环境里另一件事恰好撞上了——分清之后，要么修被测对象，要么把环境里那件事排开再验一次，并把规避办法写进操作手册。

### 56. 会话里恰好带着的变量会掩盖缺陷：测试先清掉环境再跑（2026-11-25）✅

**解决什么问题**：开发会话里有 `PYTHONUTF8=1`，所以「脚本经管道传中文路径」一直没出问题；换成操作员普通终端的环境（系统默认 GBK），`D:/项目/...` 一进管道就成了乱码路径，对账不通过。另一处：状态里的空值记成了空字符串而不是 `null`，测试只断言「读回来是空串」，两种都满足，没有区分出来。

**做法**：
1. 涉及编码、区域设置的脚本，测试开头把这些变量 `unset` 掉再跑——要验证的正是「没有它们也对」。嵌套 shell 会重新加载环境变量，清掉之后不要再套一层 `sh -c`。
2. 脚本自己把编码定下来（`export PYTHONUTF8=1`），不依赖调用者的环境。
3. 断言落在落盘的原始内容上（直接看文件里的 `"key": null`），不只看经过一层转换的读出值。
4. 工具传参会吃掉一层反斜杠：带转义的内容用写文件的工具落盘，再回读字节确认；在命令里写 Python 补丁时不要在字符串里放转义。

**为什么好**：两个缺陷都属于「在我这儿是好的」，差别只在一个环境变量和一个字符上，而且都只在失败路径上起作用。

### 57. 上线那一刻的页面：同一端口先后起两个静态服务，在真实浏览器里切一次路由（2026-11-25）✅

**解决什么问题**：路由级代码块按需加载、文件名带内容哈希。发版之后，还开着旧页面的人切到没打开过的页面，会来要已经不存在的代码块。静态服务对缺失文件回落成首页，浏览器把 HTML 当脚本执行——页面停在原处，没有任何提示。此前的兼容性测试只测了「旧页面 × 新后端」，没有测「旧页面在发版之后」。

**做法**：
1. 宿主机上起旧构建（生产现网产物的副本，后端端口改成演练的），浏览器打开并停在首页；确认目标页面的代码块还没加载。
2. 停掉，同一端口起新构建（从前端容器里 `docker cp` 出来的 dist——它只在容器里，发布目录里没有）。
3. 在页面里做一次客户端路由跳转，记录：缺失代码块的响应（状态码、类型、是不是脚本）、弹框、页面错误、刷新之后加载的入口脚本。
4. 做对照组：第二台也用旧的静态服务，确认测试能区分修复前后。
5. 「点取消」的分支也要测，并验证防重复（30 秒内不再问）。

**为什么好**：这是用户真实会遇到的时刻，而且只在发版那几分钟出现——事后在稳定的系统上永远复现不出来。

### 58. 用不上真 GPU 时，按 compose 渲染结果起一次性容器，把启动链走到「加载模型」之前（2026-11-25）✅

**解决什么问题**：演练栈不带推理 worker，「权重挂载之后能不能用」一直只比了大小和文件数。宿主上显卡 8 GB 已用 80%、虚拟机内存 6 GB，再起一个 worker 会挤到生产。

**做法**：
1. **先把调用链读准再写核对**：worker（`run_inference_worker.py` → `applications/inference/worker.py`）是在进程内（`/opt/venv`）用 `init_model` 加载模型的，第三方源码靠 `PYTHONPATH` 指向资产目录；`create_worker_app()` 启动时就会连库。我一开始以为是「起子进程、用 MMSeg310 那套 conda 环境」——那是后端容器里旧同步推理接口的链路。照错误的理解写出来的核对，第一步就对不准（推理镜像里根本没有 MMSeg310 环境）。
2. `docker compose … config --format json` 渲染出服务的环境变量和挂载，原样交给 `docker run`：同一个镜像、同一组挂载，去掉 GPU，限内存；要连库的那一步连演练网络（只通到演练库），其余不连网络。口令用演练环境文件里的临时口令，写临时文件、用完即删。
3. 逐步做：环境准备与启动脚本一致 → 依赖导入 → GDAL / PROJ 在回退环境下重投影 → worker 的自检脚本 → 候选后端的模块导入 → 应用上下文与 worker 构造（不调用 `initialize`）→ 配置解析与类型注册 → 权重用内存映射方式打开（不占内存）→ 容器内重算各项资产的 SHA256。
4. 明确写下没做的：构建模型、搬上 GPU、切片推理、矢量化、发布——列进维护窗口的强制验收项。
5. 与这次发布无关的既有问题，如实报告但不计入这次核对的判定。

**踩过的坑**（都让容器「看起来什么都没做」）：`docker run` 经标准输入送脚本要带 `-i`；挂载源必须事先存在，否则 docker 会在宿主机上就地建一个空目录（它在我的发布目录里建过一个）；挂载源不在发布目录里（`deploy/` 不进发布目录）就从工具目录挂；文件型资产比的是内容 SHA256，目录型比的是目录指纹，别混用；注册表里的类名是大写开头的驼峰，配置里小写的 `type` 是参数取值；初始化方式的注册表在 mmengine 里叫 `WEIGHT_INITIALIZERS`。

**为什么好**：不碰生产资源，却把「缺一个依赖、路径不对、权重对不上」这一类问题在窗口之前排掉；没覆盖到的边界也写清楚了。这次还顺带查出一条旧接口本来就跑不通。

### 59. 「只比大小和文件数」的核对要升级成内容比对：同一个文件在宿主机和容器里名字可能不一样（2026-11-25）✅

**解决什么问题**：资产核对一直只比大小、文件数和宿主机上算的指纹。第一次在容器内重算 SHA256，5 个目录型资产全部对不上——看着像权重被换了。

**做法**：
1. 先别下结论，挑最小的一个资产，把两边的文件清单和逐文件哈希导出来对比：10 个对 10 个、内容全同，只有 5 个的名字差一个字符。
2. 查这个字符是什么：宿主机上是 U+F03A（MSYS 用来表示冒号的私有区字符），容器里是普通冒号。再数一遍范围：5 个目录里共 2,995 个，全是下载标记文件。
3. 修在算法上（指纹里的名字按容器里看到的算），不改资产内容；指纹算法升版本，旧缓存作废；两个发布目录重建后重核。
4. 反向验证：把归一化去掉，新测试报红。

**为什么好**：内容其实一直是好的，问题在核对工具。如果不做这一步，上线后第一次带 SHA256 的核对就会报 10 项不符，把人引向「权重被替换」的错误方向。

### 60. 续接被压缩的会话：摘要里的「已完成」先和磁盘对一遍（2026-11-25）✅

**解决什么问题**：摘要写着切换脚本「已整体重写、语法检查通过」，磁盘上却是更早的未完成草稿（含未定义变量）。照着摘要往下做，会带着一个不能用的脚本进演练。

**做法**：
1. 接手任何「摘要说已做完」的东西，先读盘上的现状（行数、指纹、`git status`、实际内容），再决定下一步。
2. 文件被脚本改过之后，编辑工具要重新读一遍再用；读文件用正斜杠路径。
3. 演练环境复位要库和存储一起复位：新库配旧存储，后端启动时的迁移会因目录已存在崩一次。
4. compose 文件用了 YAML 合并键（`<<:`），自己 `yaml.safe_load` 读不到继承来的字段（会误判成「没有健康检查」）——要看定义就用 `docker compose config` 的渲染结果。
5. `docker exec … /opt/conda/…` 这类容器内路径，在 Git Bash 里要先设 `MSYS_NO_PATHCONV=1`，否则被改写成 Windows 路径。

**为什么好**：省下的不是技巧，是被误导之后的返工。

### 61. 演练栈要包含所有会被重启的组件；演练通过不等于切换顺序在生产上没有资源冲突（2026-11-25）✅

**解决什么问题**：演练栈为了省资源不带推理 worker，切换脚本在演练里七次全部顺利。生产切换时，第一阶段重启推理 worker（启动即把模型加载到 GPU，要在宿主内存里临时展开 1.84 GB 权重），脚本看到它健康就立刻开始构建 GeoView（占 1–2 GB）；虚拟机一共 6 GB，权重加载报 `Cannot allocate memory`，worker 进程退出、被重启策略拉起，连崩 3 次，直到构建结束才加载成功。同一天的接口冒烟里还有一条：经宿主发布端口发送超限请求体，客户端一直等不到响应，而演练栈上同一条 11 毫秒就返回。

**做法**：
1. 演练前先列出"这次操作会重启哪些进程、每个启动时吃多少内存、峰值会不会重叠"。内存或显存峰值重叠的阶段，要么在演练里真跑，要么把顺序排开（构建在前、加载模型的在后），不要因为"演练栈没有它"就跳过。跳过了的组件，至少在动生产之前到它的容器里只读试跑一遍切换要用到的命令。
2. 请求行为在演练和生产上不一样时，先分层定位：同一个请求分别从宿主经发布端口、从容器网络内直连各发一次。两边结果不同就是传输层（端口转发、代理）的事，不要去改应用。演练栈的端口只绑回环地址时走的是另一条转发路径，结论不能直接搬到生产。
3. 判断"模型上了 GPU"不要用"推理时显存上升"：常驻显存的模型推理一个小图块不会抬高显存。用未加载模型与加载后的整机显存对比，加上按设备查询的 `effective_device` 和利用率峰值。

**为什么好**：这两处都不是代码缺陷，而是"演练环境比生产少了东西"造成的盲区。把演练覆盖面按"会被重启的进程"来定义，比按"功能"来定义更不容易漏。
