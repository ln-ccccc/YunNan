# 测试方法手册：技巧积累与采纳记录

本手册记录本项目沉淀下来的测试技巧、想不出测试思路时的检查单、以及对外部测试方法的采纳标准。它回答的是「**怎么想到这样测、为什么这样测是好的**」；选哪类测试、跑什么命令见 [开发规范第 6、7 节](development-standard.md#6-测试按风险选择)，两者不重复维护。

**为什么需要这份手册**：测试思路不是每次都能现场想出来。可靠的来源只有三种——本项目踩坑实录（最可信，附真实案例）、外部方法（必须过第三节的标准才能收）、以及两者的定期回顾。收录一切条目的共同底线：**说得出它比现有做法多抓住哪一类缺陷，并举出实例或写出可判定的验证实验，不凭"感觉有用"。**

每条技巧按固定格式记录：**解决什么问题 → 做法 → 为什么好 → 本项目实例（含日期）**。状态分三级：✅ 已验证（有本项目实测案例）、🧪 候选（写明验证实验，实验完成前不进规范）、❌ 已淘汰（保留淘汰理由，防止重复试错）。

---

## 一、已验证技巧

### 1. 递进测试：单文件 → 小批量 → 全量 ✅

**解决什么问题**：只跑单个用例或单文件时全绿，给人虚假信心；而环境、契约、多模块交互类问题只在更大范围暴露。

**做法**：按「单文件 → 相关模块小批量 → 全量 discover/全量套件」三级递进，每级通过才升级，失败就地定责后再继续。

**为什么好**：不同缺陷的爆炸半径不同——模块逻辑错在单文件暴露；fixture 路径、模块间契约在小批量暴露；环境配置、测试漂移、没人跑过的死角在全量暴露。三级各自覆盖一类，不可互相替代。且递进的成本极低：失败时范围越小，定位越快。

**本项目实例（2026-09-07）**：后端单文件 17/17 绿 → 小批量抓到「只挂 backend 漏了仓库根 tests/fixtures」的挂载错误 9 例 → 全量 299 例再抓出 7 个问题，其中 2 个是 `main` 上就存在的测试漂移，单文件和小批量都测不到。 miner 侧 13 → 12 → 60 全绿作对照。

### 2. 红灯验证：先证明测试能失败 ✅

**解决什么问题**：新写的测试可能永远通过（断言太弱、守卫没生效、测试对象接错），这样的测试是摆设。

**做法**：写完测试后，临时移除/还原被测的修复，确认测试**恰好失败在预期的那条上**，再恢复修复确认全绿。git stash 单文件即可完成，不动其他未提交内容。

**为什么好**：一个"修没修都绿"的测试给出的通过是噪声。红灯验证把「测试确实在被测行为上打钩」从感觉变成证据；且能验证失败信息本身可读（失败时打印的是不是人能看懂的原因）。

**本项目实例（2026-09-07）**：BFF `file_path` 守卫测试——stash 掉路由改动后恰好 12 过 1 挂（只有新测试红）；MapDashboard 生命周期测试——还原组件后 0 过 1 挂。两次红灯形态都符合预期才提交。

### 3. 安全守卫测试三件套：拒绝 + 上游计数为零 + 合法对照 ✅

**解决什么问题**：守卫测试常见两个漏洞——只断言了 422 却没发现请求仍被转发（副作用照常发生）；只测了拒绝，守卫写严了把合法请求也拦了却没人知道。

**做法**：一条测试同时断言：① 返回 422/400；② 用调用计数 fake 断言上游 client **调用次数为 0**（请求根本没出去）；③ 另配一条合法载荷的对照测试，断言放行且转发内容不被篡改。

**为什么好**：状态码只能证明 HTTP 层行为，计数为零才证明「拦截发生在这一层」；合法对照防过度拦截。三条合起来才构成守卫行为的完整定义。

**本项目实例（2026-09-07）**：`file_path` 守卫测试按项目负责人要求补了「未转发 Flask」断言（`createProjectDataset` 与 `request` 计数均为 0），并为 `storage_key` 合法登记加了转发不变对照。此前 `output_dir` 守卫测试（`projectRoutes.test.js`）已是这个形态，直接沿用了它的模式。

### 4. 生命周期泄漏：抽成配对纯函数再动态验证 ✅

**解决什么问题**：事件监听器、定时器、观察者这类「注册-注销」资源，写在组件里时单测框架够不到；泄漏（只注册不注销）在单测里永远发现不了。

**做法**：把注册/注销逻辑抽成 `createXxx` 纯 JS 工厂（返回 attach/detach 配对方法），组件只负责在挂载/卸载钩子里调用。测试用 stub 目标模拟 N 轮挂载/卸载循环，逐轮断言「挂载时恰 1 个监听、卸载后归零」，并验证事件送达恰一次、注销后不再送达。

**为什么好**：泄漏的本质是「注册与注销不配对」，只有动态模拟循环才能证明配对性；抽成纯函数后用仓库现有的零依赖 node:test 就能测，不需要引入 Vue 测试栈。成本极低（本次 12 行模块），且组件代码因此更简单。

**本项目实例（2026-09-07）**：MapDashboard 的匿名 resize 监听器泄漏 → 抽出 `createWindowResizeListener`，测试模拟 3 轮挂卸循环逐轮断言归零（`windowResizeListener.test.js`）。

### 5. 源码结构断言：锁 SFC 内的不变量 ✅

**解决什么问题**：Vue 单文件组件的内部写法在无组件测试依赖的环境里无法行为级测试，但某些约束（"禁止再做 X"）需要防止回归。

**做法**：按 `mapContainerLifecycle.test.js` 的既有模式，用正则对 `.vue` 源码断言结构（如"必须在 onUnmounted 里 detach"），配一条 `doesNotMatch` 禁止匿名注册。

**为什么好**：这是行为测试够不到时的降级手段，比没有强——它至少能保证「回归发生时测试会红」。但要清楚它的边界：只证明代码长这样，不证明行为正确。**与技巧 4 的分工**：逻辑能抽就抽出去行为级地测（优先），抽不出去的用结构断言锁约定。

**本项目实例（2026-09-07）**：`mapDashboardLifecycle.test.js` 三条断言与技巧 4 的动态测试互补：动态测试证明机制正确，结构断言证明组件确实在用这个机制。

### 6. 环境陷阱：失败聚类 → 最小复现 → 显式记录命令 ✅

**解决什么问题**：环境造成的批量误报（依赖缺失、资源路径、行尾格式）极易被误判为代码回归，浪费排查时间并消耗对测试的信任。

**做法**：三步——① **聚类**：大量失败共享同一错误家族（如全部是 CRS 相关）时优先怀疑环境；② **最小复现**：用一行代码验证假设（如 `ImportFromEPSG(4326)` 是否返回 0）而不是跑全量试错；③ **显式记录**：把能跑通的完整命令和陷阱签名写进文档，让下一个人不重踩。

**为什么好**：环境失败的特征是「同一根因、多处爆发、代码无关」。聚类+最小复现把几小时的试错压缩成几分钟的验证；记录命令把个人经验变成团队资产。

**本项目实例（2026-09-07）**：容器内 9 例 CRS 集体误报 → 一行 `ImportFromEPSG(4326)` 证实 PROJ 资源路径缺失 → 结论「必须先 conda activate」连同完整命令写入开发规范第 7 节。同日：CRLF 行尾（`file` 命令看到 `^M$`）导致的 2 例 bash 契约误报同理。

### 7. 被吞异常：在断言点取证 ✅

**解决什么问题**：代码里宽泛的 `except` 会把真实异常转换成另一个表面症状（如任务被标为 failed），测试报的错（`KeyError: 'result'`）不是根因。

**做法**：当失败断言读的是「调用参数」而代码里有宽泛 except 时，不要猜——在容器/本地复现同样的调用，把 mock 收到的实际参数打印出来（`call_args.kwargs`），被吞的异常通常就在 `error_message` 里。

**为什么好**：从表象（finish_job 没有 result 参数）到根因（`KeyError: 'classification_results'`）隔着一次异常转换；取证比顺着表象猜快得多，且证据是打印出来的实参，不是推断。

**本项目实例（2026-09-07）**：`test_inference_runner` 的 `KeyError: 'result'` → 容器内复现打印 `finish_job kwargs` → 得到 `error_message: 'classification_results'` → 定位到测试 mock 缺字段（见技巧 8）。

### 8. git 考古定责：代码漂了还是测试漂了 ✅

**解决什么问题**：测试失败后必须回答「是生产代码坏了还是测试过时了」，答案决定修哪边；猜错方向会把正确代码改坏。

**做法**：对涉事的代码文件和测试文件分别查最后修改的 commit 及其内容。若「代码新增了契约、测试停留在旧契约」，就是测试漂移——修测试；反之才是代码缺陷。

**为什么好**：几条 git log 就能把"疑似 bug"收敛成"测试漂移"，避免无谓的生产代码"修复"。这也是回归测试长期维护的核心动作：契约演化后测试要跟着长。

**本项目实例（2026-09-07）**：`inference_results.py` 最后改于 `72d5764`（新增 `classification_results` 返回字段），`test_inference_runner.py` 停留在基线 `e3c407f` → 判定测试漂移，生产代码正确。同日 `test_inference_image_contract` 对 `APP_IMAGE` 的旧期望值同类。

### 9. 数据限制：只读挂载资产做证明 ✅

**解决什么问题**："测试失败可能是因为缺权重/缺数据文件"如果不验证，就永远是不确定的猜测，测试基线立不起来。

**做法**：把缺失的运行资产从宿主机（main 工作区）**只读挂载**进容器，重跑失败用例。通过 → 证实纯数据限制，记入已知失败台账；仍失败 → 排除数据因素，继续查。

**为什么好**：把「大概是缺数据」变成实验结论。只读挂载满足项目「原始资产只读共享」的规则，不复制、不污染源工作区。

**本项目实例（2026-09-07）**：挂载 `backend/model/*.pth`（1.9G）与 `miner/yunnan.kml`（3.2M）后，`test_inference_runner` 与 `test_yunnan_project_seed` 各 1 例由错转绿，坐实数据限制分类。

### 10. 黄金样例 fixture：固定 ID 与时间、整 JSON 比对 ✅

**解决什么问题**：断言逐字段手写容易漏字段、且随实现漂移；动态 ID/时间戳导致测试脆弱或诱导开发者"删掉动态字段再比"，比了寂寞。

**做法**：把接口的完整期望响应固化成 JSON 文件（固定项目 ID、固定时间或不含时间），测试里做**整 JSON 深比较**，不删任何动态字段。fixture 放仓库级共享目录，后端与 BFF 测试共用同一份。

**为什么好**：整 JSON 比对让「多返回了一个字段」这种契约变化立刻红；共用 fixture 保证 Flask 与 BFF 两层验的是同一个契约，契约变更必须改 fixture 才能过测试——这正是契约该有的严肃性。

**本项目实例**：`tests/fixtures/project-hub-v1/` 六个样例（blocked/partial/ready/assets 系列），`test_project_read_models.py` 17 例与 `projectRoutes.test.js` 透明代理测试共用；2026-09-07 全部解析与比对通过。

### 11. 连续运行验证：单次通过不算通过 ✅

**解决什么问题**：「执行一次」型的验证（推理、导入、导出、备份恢复）单次成功掩盖了状态清理与资源回收缺陷——临时目录、连接、句柄、模型/缓存的残留会污染第二次执行，线上表现为"每次启动只能跑一次，第二次必崩"。

**做法**（三级递进，源自江西 AGENTS.md §5.1，云南 2026-09-08 引入）：① **重复执行**——同一操作连续跑第二遍，第一遍验功能，第二遍验状态清理与资源回收；② **混合小批次**——抽样 ≥3 组不同形态输入串行执行，验证逐项隔离与累积效应；③ **全量回归**。三级通过才算该操作验证完成。

**为什么好**：第一遍和第二遍执行的代码路径通常相同，但进程状态不同；泄漏、残留、单例污染这类缺陷只会在第二遍及以后显形。让"再跑一遍"成为验收的硬性动作，成本极低，专抓一类极常见且单次验证永远抓不到的缺陷。

**本项目实例（2026-09-08）**：推理 worker 韧性移植（参考江西 EPIPE 事故「每次启动只能完成一次推理」）——容器内同一 worker 实例连续两次真实 CPU 推理（预载模型 + 真实流水线）均成功，进程内毒载荷/目录冲突混合序列回归测试锁定隔离行为；该事故类别从此有回归护栏。

### 12. 多视口布局扫描与渲染伪影甄别 ✅

**解决什么问题**：两类问题单靠"肉眼看页面"都难以定位——①布局在小视口/低分辨率下溢出或元素重叠；②页面本身没坏，但**渲染层出伪影**（整页内容平铺成多份、互相重叠、截图超时），两者症状看起来都是"界面乱了"，处理方向完全相反。

**做法**：
1. **DOM 优先定责**：先在页面上下文里做量化几何检测，不看截图——`document.documentElement.scrollWidth > innerWidth` 判水平溢出；对 `section/aside` 等面板两两算 `getBoundingClientRect()` 矩形相交面积（>8×8px 判重叠）；再查 `scrollWidth/transform/zoom/DevicePixelRatio` 异常。
2. **分级定责**：DOM 几何有问题 → CSS 断层，修样式；DOM 几何干净但截图/显示乱 → 渲染合成伪影，查 GPU 合成触发器（`backdrop-filter`、`filter`、`will-change`、大面积动画），逐个禁用对比截图。
3. **多视口扫描**：对 1366×768 / 1280×720 / 1024×640 三档逐视口重复检测，覆盖不同宿主环境。

**为什么好**：几何检测把"看起来乱了"变成可判定的数字（相交像素、溢出值），直接区分"修 CSS"还是"修渲染触发器"——本案（2026-09-09）程序化扫描证明布局三视口全绿，从而避免了一场无方向的 CSS 大改，精确定位到 3 处 `backdrop-filter`。
**本项目实例**：地图侧栏/顶栏的毛玻璃效果在 ZCode 内嵌浏览器触发整页平铺伪影（且伴随 dpr=0.9999 异常、截图超时），移除 backdrop-filter 后三视口扫描清零（`b3a5cdb`）。
**注意**：内嵌浏览器的截图功能本身可能超时或产出平铺伪影——**视觉验收以真实浏览器为准，自动化以几何检测为准**，不要用可疑截图反推 CSS 结论。


### 13. 滚动链审计：滚轮失灵与内容不可达 ✅

**解决什么问题**：页面内容比屏幕高，但滚轮怎么滚都没反应——下半部分功能（按钮、表单、列表）用户永远够不着。这类问题不会让测试失败、不报任何错，只有真人滚动时才会暴露。

**做法**：
1. **滚动链审计**（在页面上下文执行）：从光标处元素沿祖先向上走，逐层记录 `overflowY`、`scrollHeight` 与 `clientHeight`。Bug 特征签名：**内容比视口高（scrollHeight > clientHeight），但整条链上没有任何一层允许滚动**（全是 visible/hidden）——说明溢出内容被裁掉且无处滚动。
2. **修复后验证**：确认滚动链上出现可滚动层（`overflowY=auto/scroll` 且 `scrollHeight > clientHeight`）；程序化设置 `scrollTop` 后，目标元素 `getBoundingClientRect()` 应进入视口。
3. **注意验证手段的坑**：合成 `WheelEvent` 不会触发浏览器原生滚动（不可信事件的默认滚动行为不执行）——滚轮行为要么用真实输入模拟验证，要么以「滚动容器存在 + scrollTop 可驱使内容进视口」为判定依据；内嵌浏览器输入管线不稳时，程序化断言是可靠的验收口径。
4. **设计期预防**：凡 `height: 100vh` 的固定外壳，必须同时回答"内容比一屏高时从哪里滚"；配合全局 `body { overflow: hidden }` 时尤其危险——两层都堵死就是本案。

**为什么好**：滚动失灵零报错、零测试失败，肉眼不滚动就发现不了；滚动链审计把它变成 3 行可判定的数字（每层的 overflow/scrollHeight/clientHeight），30 秒定位，且能精确指出"该在哪一层补 overflow"。

**本项目实例（2026-09-09）**：项目工作台内容高 1897px、视口 768px，`body{overflow-y:hidden}` + 工作台外壳 `height:100vh` 无 overflow，用户滚轮失灵、下半页面板（资产/活动/导出）永远够不着。修复：仅给工作台外壳加 `overflow-y: auto`（`2739884`）；修复后滚动 600px 底部面板进入视口（scrollTop 可驱使），地图视图的满屏不滚布局不受影响。


### 14. 容器内测代码：用 git archive 传输，不信 bind mount 与 docker cp ✅

**解决什么问题**：Windows 上通过 bind mount 或 `docker cp` 把代码送进容器测试时，gRPC-FUSE 缓存可能返回**陈旧文件内容**——同一份代码"有时测试全绿、有时莫名失败"，或者"修了没生效"，极难排查。

**做法**：测试用的代码一律经 `git archive` 从 git 对象库导出（git 自校验，绕过文件系统缓存）：

```bash
git archive --format=tar -o /tmp/code.tar HEAD backend
docker cp /tmp/code.tar 容器:/tmp/
docker exec 容器 bash -c "cd /tmp && tar xf code.tar && cd backend && python -m unittest ..."
```

**为什么好**：git 对象库读取内容哈希自洽，永不陈旧；tar 传输一次到位，避开挂载层。配套两条纪律：①容器内测试报错与宿主机直跑不一致时，**先怀疑文件内容不同**（容器内 `hashlib` 对比或 `inspect.getsource` 打印执行中的源码），再怀疑代码；②只在 git 追踪的提交上做"定义性验证"，临时实验标注清楚。

**本项目实例（2026-09-10）**：批量前向开发的验收测试，docker cp 路径下 5 项测试稳定报 `KeyError: 'out_name'`（陈旧字节里的旧代码），改用 `git archive` 后同套件全绿——同一秒内两种传输方式结果相反。已写入开发规范作为容器测试的标准传输方式。

## 二、想不出测试思路时的检查单

按顺序过一遍，每条给出「提示自己」的问题和本项目实例。多数卡壳是忘了其中两三条。

1. **输入空间划分**：合法输入的边界在哪（空、零、超长、小数、Unicode、Windows 盘符、`..`）？非法输入的每个等价类各挑一个代表了吗？——例：`storage_key` 校验测了 `..`、`D:/`、绝对路径、大小写后缀。
2. **反向与未发生**：除了"该发生的发生了"，"不该发生的没发生"验证了吗（上游调用计数为零、无副作用、无多余字段输出）？——例：守卫三件套（技巧 3）、资产响应不含物理路径键的递归断言。
3. **状态机**：对象有哪些状态？每个转移触发了吗？**终态之后的行为**（终态任务不再当进行中）和**非法转移**（重跑同年、重复 FID）测了吗？——例：`vector_status` 转移、空间任务终态回退向导。
4. **竞争与时序**：两个请求交错、旧响应晚到、轮询期间切换对象，最新选择还能赢吗？——例：`createSelectionGate` revision token。
5. **故障注入**：依赖抛错、返回缺字段、返回错误码、超时、OOM 时，行为是可控失败还是崩溃/静默错？——例：publisher mock 缺字段暴露的契约问题（技巧 7）、GPU 失败回退 CPU。
6. **资源生命周期**：注册的东西注销了吗？反复进出 N 轮还平衡吗？——例：resize 监听（技巧 4）。
7. **失败不留半份成果**：中途失败后，磁盘上有没有残留的半成品？重试会不会叠加脏数据？——例：导出失败清目录、发布失败回滚备份。
8. **兼容与回归**：旧字段/旧接口形状还在吗？修 bug 前先写一个在旧代码上失败的新用例了吗？——例：红灯先行（技巧 2）、旧 `status` 与 `lifecycle_status` 并存断言。
9. **换一层验证**：单元过了，BFF 层转发还是原样吗？fixture 两层共用吗？全量套件里它还绿吗？——例：递进测试（技巧 1）。

## 三、外部方法的采纳标准与候选区

**采纳四标准（全部满足才从候选升为已验证）**：

1. **缺陷类别明确**：能说出它比现有方法多抓哪一类缺陷，抓不到已知缺陷类别的不收。
2. **可落地**：在本项目工具链上可行，新增依赖、运行时间、维护成本列得清楚。
3. **验证实验可判定**：写明「引入后若能抓到 X / 证明 Y 则采纳，否则淘汰」，实验做完留结论。
4. **来源可信**：官方文档、实证研究或本项目实测优先；转述口碑需注明。

### 🧪 property-based testing（Hypothesis）

**它多抓什么**：人写示例测试靠枚举，等价类想漏就漏；property-based 生成成千上万输入（自动包含空串、NaN、Unicode 等刁钻值）并**把失败输入收缩成最小复现**，本质是"搜索我们误解代码的方式"（[官方文档](https://hypothesis.readthedocs.io/)；Anthropic 用它抓到过 numpy 真 bug 的[实验记录](https://www.anthropic.com/research/property-based-testing)）。

**验证实验**：对 `isSafeIncomingTiffStorageKey` / `_validate_incoming_tiff_storage_key` 这类路径校验函数跑一轮 property（"任何不在 `incoming/*.tif` 白名单内的输入必须被拒"）。找到绕过样本 → 采纳；一轮无增益 → 记"未增益"留档。**成本**：测试环境新增一个 dev 依赖。

### 🧪 mutation testing（mutmut）

**它多抓什么**：红灯验证（技巧 2）一次只能人工验证一个改动；mutation testing 把这件事自动化——算法改写源码（`==`→`!=`、删返回值等）生成"变异体"，**变异体存活 = 断言缺口**，直接量化测试强度（[官方文档](https://mutmut.readthedocs.io/)；其度量的是测试质量而非代码质量，见 [Codecov 实操文](https://about.codecov.io/blog/getting-started-with-mutation-testing-in-python-with-mutmut/)；学术对比见 [ACM 2024 四工具评测](https://dl.acm.org/doi/10.1145/3701625.3701659)）。

**验证实验**：挑断言密集的 `readiness.py` 或 `assets.py` 跑一轮，人工核对存活变异体是否对应真实断言缺口。缺口发现率高 → 采纳为季度性检查；存活解读成本过高/误报多 → 淘汰。**成本**：运行时间长（每个变异体跑一次测试），不适合进日常循环。

### 🧪 coverage 作缺口探测器（非指标）

**为什么这么定位**：覆盖率 100% 的测试可以全是无断言的摆设，把覆盖率当 KPI 会诱导写垃圾测试；但反过来，**分支覆盖数据能直接指出"从来没测过的路径"**（尤其错误分支），作探测器无害且便宜。**验证实验**：后端跑一次分支覆盖，人工核对未覆盖分支是否真为死代码/低风险；若能定位出遗漏的真实分支则保留为排查工具。**成本**：仅需 coverage 依赖，一次性运行。

### ❌ 已淘汰（保留理由防止重复试错）

- **Pact 类独立契约测试框架**：本项目前后端同仓、已有共享黄金 fixture（技巧 10），框架带来的 broker/多语言设施远超单人团队收益，违背 AGENTS.md「不为未来假设增加抽象层」。
- **浏览器像素级快照测试**：维护成本高、对无关渲染抖动过敏；UI 验收由人工浏览器走查 + 组件结构断言覆盖，快照与 fixture 职责重复。

## 四、维护约定

- **何时追加**：每次测试抓到「以前没见过」的缺陷类别、或某方法在本项目被实测证明/证伪后，由当次会话起草条目并提交，负责人审阅。
- **升降级**：候选条目完成其验证实验后升级为已验证（附实验结论）或降为已淘汰（附理由）；已验证条目若连续两次实战无增益，降级并记录。
- **分工**：命令与"选什么测"归开发规范第 6、7 节；方法论、理由与历史案例归本手册；测试进度与定责台账归各计划文档，不在本手册重复。
- **写条目的纪律**：没有实例或实验的条目不进"已验证"；"感觉有用"不是收录取证。
