# 发布隔离：源码从发布目录挂载，部署与回滚手册

2026-11-25。适用于矢量编辑这一轮上线，以及之后任何一次"把一个确定的提交放到生产上"的操作。
发布前的最终检查结果与上线检查表见 [发布前最终检查与 Go / No-Go 检查表](release-go-no-go-20261125.md)。

配套工具都在 `deploy/` 下，用法与每一步核对什么，见各脚本开头的说明：

| 工具 | 做什么 |
| --- | --- |
| `deploy/make_release.sh <commit>` | 从一个固定的提交生成发布目录 |
| `deploy/switch_release.sh <发布目录>` | 切到这份发布目录，切完自动核对；写配置之前先对账、查任务，失败时给出恢复命令；回滚也是它 |
| `deploy/verify_release.sh <发布目录>` | 只读核对运行中的栈是不是这份发布目录；`--hash-assets` 在容器内重算资产的 SHA256 |
| `deploy/release_tool.py` | 上面三个脚本共用的工具（记账、核对、钉住版本、查任务、切换状态）；测试 `python -m unittest discover -s deploy -p "test_release_tool*.py"` |
| `deploy/rehearsal/` | 隔离演练的覆盖文件与环境文件模板 |
| `docs/deployment-release-isolation.md`（本文） | 生产现状、方案、操作顺序、回滚、演练怎么做、运行时资产怎么迁出开发树 |

## 2. 方案

把容器挂载的东西分成三类，各走各的路：

| 类别 | 内容 | 从哪里来 | compose 里怎么写 |
| --- | --- | --- | --- |
| 代码 | 容器挂载的全部源码：`backend`、`docker`、`config.yaml`、`frontend/src` 与 `package.json`、`miner` 的五个路径 | 发布目录（一个固定提交的导出） | `${YUNNAN_SOURCE_ROOT:-.}/…`，共 25 处 |
| 运行时资产 | 不入库的推理权重（7.4 GB）、预训练骨干权重与随附的 `mmseg`、`dinov3` 源码目录、四个旧模型目录，共 9.46 GiB | 资产目录，默认就是开发主树 | `${YUNNAN_ASSET_ROOT:-.}/…`，三个挂后端代码的服务各 7 处 |
| 数据 | `project_storage`、离线底图、`miner/yunnan.kml` 与四个 xlsx | 不变 | 保持相对 compose 文件所在目录 |

两个变量都**不设置时，渲染结果与改造前逐项相同**（把新旧 compose 文件各渲染一次逐字段比对过：7 个服务的原有挂载
与其余字段完全一致，只多出 21 处只读的资产挂载）。

为什么要分出"运行时资产"：生产后端与两个 worker 读的权重、以及启动脚本加进 `PYTHONPATH` 的 `mmseg`、`dinov3`
源码，都不在任何提交里（被 `.gitignore` 忽略）。此前它们是靠"整个开发树一起挂上去"带进容器的；源码改从
发布目录挂载后，发布目录里没有这些文件，容器能起来，但推理会找不到权重。演练第一次启动就是在这里暴露了
另一件事：命名卷 `backend-static` 挂在只读的 `backend` 之上，挂载点目录在发布目录里不存在，只读文件系统里
建不了，后端直接起不来。

### 发布目录里有什么

`deploy/make_release.sh <commit>` 做四件事：

1. **归类检查。** 把开发树的发布路径下所有未提交的条目逐个归类：运行时资产、已知的不进发布目录的东西
   （字节码缓存、本地虚拟环境、`.flaskenv`、下载标记文件等），出现归不了类的就拒绝生成——靠"整个开发树
   一起挂上去"带进容器的隐含依赖，每多一个都会在这里被拦住。
2. **导出代码。** `git archive` 导出该提交的代码路径；GeoView 依赖按 `package-lock.json` 用 `npm ci` 干净安装
   （约 37,000 个文件、约 285 MB；开发主树的依赖目录有 86,119 个文件、810 MiB，多出来的不在锁文件里）。
3. **留出空挂载点。** 命名卷的 2 个目录、运行时资产的 7 个挂载点（目录留空目录，权重文件留 0 字节文件）。
4. **记账。** 写 `RELEASE.json`：提交号与说明、生成时间、每个代码路径的文件指纹、每个运行时资产的大小 /
   文件数 / SHA256、GeoView 依赖的文件数、镜像编号、KML 与 xlsx 的指纹。

成品目录在仓库外，默认 `<仓库上一级>/yunnan-releases/<短提交号>-<UTC 时间>`，每个约 0.25 GB，主要是 GeoView 依赖。
生成之后不要再改它；要换内容就重新生成一份。

资产指纹第一次要读 10 GB（本机实测 19 秒），之后按（路径、大小、修改时间）走缓存，没变就不重算。

**目录指纹里的文件名按容器里看到的名字算。** Windows 上 MSYS 把名字里的冒号记成私有区字符 U+F03A
（下载标记 `x.pth:Zone.Identifier` 就是这样），Docker Desktop 挂进容器后又是普通的冒号。宿主机生成、容器内
核对用的是同一份脚本，名字都按冒号算，两边的指纹才对得上（2026-11-25 容器内重算 SHA256 时查出，见第 6 节）。

## 3. 上线操作

前提：代码已经在某个提交里；该提交的测试已通过；发布目录已生成并 `deploy/release_tool.py check` 通过。
**以下每一步都会重启生产容器，须负责人确认后执行。**

```bash
cd /d/项目/YunNan

# 1) 生成两份发布目录：回滚用的基线，和要上的版本
deploy/make_release.sh 820dd50            # 回滚基线（本轮）
deploy/make_release.sh <要上线的提交>

# 2) 切换之前：备份数据库与存储、单独备份配置文件（备份脚本不含它们）、确认没有推理 / 切片任务在跑、通知用户

# 3) 切换。第一次切换用 --rollback-target 指明"出问题回到哪一份"；--hash-assets 让收尾的核对在容器内重算资产 SHA256
deploy/switch_release.sh D:/项目/yunnan-releases/<要上线的目录> \
  --rollback-target D:/项目/yunnan-releases/<基线目录> --hash-assets
```

**脚本从哪里运行。** compose 文件和环境文件取自 `--project-dir`（默认是脚本所在的仓库目录），切换脚本和它用的工具取自脚本
自己所在的目录。上面的写法前提是本轮的提交已经合入主树。**没有合入主树也能上线**：从放着新脚本的那个工作树运行，
用 `--project-dir` 指向主树（compose 文件和 `.env` 在那里）。之后回滚也同样带上 `--project-dir`：

```bash
D:/项目/YunNan-vector-release/deploy/switch_release.sh D:/项目/yunnan-releases/<要上线的目录> \
  --project-dir D:/项目/YunNan --rollback-target D:/项目/yunnan-releases/<基线目录> --hash-assets
D:/项目/YunNan-vector-release/deploy/switch_release.sh --rollback --project-dir D:/项目/YunNan
```

主树里的旧版切换脚本不能用：它先写 `.env` 再对账，也没有回滚状态。

`switch_release.sh` 依次做：

1. **核对发布目录自身**（代码指纹、依赖与锁文件、空挂载点、资产目录）。
2. **用目标目录渲染 compose 配置并对账**（此时 `.env` 没有动）：源码挂载全部指向发布目录、资产挂载指向资产目录、
   **数据挂载与现有容器完全相同**。任何一处不同都停下。
3. **查库**确认没有排队或运行中的推理 / 切片任务；有就停下（确认是可以中断的残留任务，用 `--allow-running-jobs`）。
4. **把 `YUNNAN_SOURCE_ROOT` 和 `YUNNAN_GIT_SHA` 写进 `.env`**，只动这两行，其余字节不变。钉在 `.env` 里而不是只靠
   这一次命令的环境变量：之后任何人按旧习惯执行 `docker compose … up -d`，读到的也是同一个源码目录。
   写完再渲染一次，必须与第 2 步对账过的那份逐字节相同，否则立刻把 `.env` 改回原样。
5. **分阶段切换：后端与两个 worker → GeoView → Miner 适配层与界面。** 每一阶段等到健康才进下一阶段。
6. **核对运行中的栈**（同 `verify_release.sh`；带 `--hash-assets` 时包含容器内的资产 SHA256）。

切换会重建全部挂了源码的容器（5 个应用容器加 2 个 worker）。GeoView 在容器里从头构建，冷缓存时要四五分钟，
期间健康状态会先变成"不健康"、构建完再恢复，这是正常的；脚本会等到它健康。

### 失败安全

- **前三步只读。** 写 `.env` 之前无论哪一步失败，`.env` 一个字节都不动，也不起任何容器。
- **写过 `.env` 之后的任何失败（包括按 Ctrl-C）**，脚本都会报出 `.env` 现在指向哪一份，并给出可以直接照着执行的恢复命令。
- **不自动回滚。** 失败原因可能是磁盘、内存这类外部因素，再切一次未必更好，由人判断。
- **所有等待都有上限：** 查任务 30 秒；每次 docker 调用（含 `compose up`）5 分钟；容器内重算资产 SHA256 1 小时；
  每个阶段等健康 `--timeout`（默认 900 秒）。容器退出或反复重启时立即判失败，不等到超时。

### 切换状态文件

每次切换都在 `<发布根>/.switch-state.json` 里记一笔（与发布目录放在一起，在仓库之外）：
`current`（上一次成功切到的）、`previous`（它之前的那一份）、`restore_to`（这一次要是没完成，应回到哪一份）、
`last_attempt`、`last_attempt_status`（`in_progress` / `succeeded` / `failed` / `aborted`）。
`--rollback` 不带目录时据此决定回到哪里（见第 4 节）。别的栈（例如演练）用带自己项目名的文件，互不干扰。

`verify_release.sh` 核对的内容：

- 发布目录自身没被动过；
- 每个应用容器：源码挂载指向发布目录且只读、**容器内的代码指纹与清单一致**、运行时资产的大小与文件数与清单一致
  （`--hash-assets`：再逐个重算 SHA256）、容器启动时间不早于发布目录、健康检查通过、镜像编号与清单相同；
- 接口：后端健康、`/api/system/version` 的 `git_sha` 等于发布目录的提交、三个几何接口存在且要求登录、
  Miner 适配层与两个前端首页可达、GeoView 产物与这个发布的源码一致；
- `.env` 里钉住的源码目录与版本就是这一份。

任何一项不符即非零退出，并写明差在哪。

### 切换之后还要人工看一眼

- GeoView：打开一条成果的编辑器，画一个面、消除锯齿、保存。
- Miner：项目工作台能打开，成果清单正常。
- 推理：跑一条小影像确认能出结果（权重挂载是否正确的唯一直接证据）。
- 已经打开的页面：停在别的页面的旧页面，切到没打开过的页面时会弹出"系统已更新到新版本"，点确定刷新即可（见第 7 节）；
  已经停在旧编辑器里的页面可以继续用，保存走新后端的校验——但它的简化不经过新引擎的精度门槛，建议通知用户刷新。

## 4. 回滚

```bash
deploy/switch_release.sh --rollback                                    # 按状态文件回到该回的那一份
deploy/switch_release.sh --rollback D:/项目/yunnan-releases/<某一份>     # 直接指定回到哪一份
```

不带目录时，脚本按 `.env` 钉住的那一份找到状态文件：

| 上一次切换 | 回到 |
| --- | --- |
| 成功 | 它之前的那一份（`previous`）；它之前没有别的发布目录，就解除钉住、回到开发树 |
| 失败或没切完 | 切换之前的那一份（`restore_to`）；此前没有钉住过，就解除钉住、回到开发树 |
| 在写 `.env` 之前就停了（`aborted`） | 什么都不用做 |

**生产第一次切换务必带 `--rollback-target`。** 此前 `.env` 没有钉住过任何发布目录，不给的话出问题只能解除钉住、
回到开发树——而开发树的 HEAD 可能已经走到别处。

**不要用"去掉 `YUNNAN_SOURCE_ROOT`"当回滚。** 那会让容器回到开发主树，而主树可能已经前进到别的地方。

**回滚目标是什么，要心里有数。** 本轮的回滚目标 `820dd50` 是上一轮的几何引擎（固定容差 1e-5 度、只校验合法性）
和它配套的 GeoView。它**不是**此刻生产内存里的那个版本：生产是一个混合版本（第 1 节），无法精确复现；
`820dd50` 与后端所在版本之间隔着 11-13 至 11-24 的一大批提交，它从未在生产上跑过，只在隔离演练里两次完整切换并核对通过。

**回滚不动数据。** 切换与回滚只换挂载的代码，不写数据库、不删文件；上线之后新增的成果修订、审计记录、导出都还在。
回滚后的代码读得懂这些数据：`12b79de` 之后到候选之间，数据库模型、迁移脚本、种子脚本没有任何改动。

回滚后的兼容性在隔离演练里用真实浏览器验证过（见第 6 节）：回滚当刻已经打开的新页面，保存照常，点"消除锯齿"
会提示简化失败（旧后端没有这个接口）。

## 5. 隔离演练怎么做

不要直接在生产上试第一次切换。`deploy/rehearsal/` 提供了一套与生产完全隔离的演练栈：独立的 compose 项目名
`yunnan-rehearsal`、独立的容器名、命名卷、网络、端口（只绑 127.0.0.1 的 23000 / 24000 / 25008 / 28000）、
独立的临时库和空的存储目录；不带推理 worker。

主文件里有三类东西是写死的，只换项目名挡不住，覆盖文件里逐项盖掉了：`container_name`（否则与生产容器重名）、
命名卷的 `name`（否则直接挂上生产的 `yunnan_mysql_data`）、`ports`（compose 对端口是追加，必须 `!override`）。

```bash
# 1) 准备环境文件：照 deploy/rehearsal/rehearsal.env.example 填，放在仓库之外，口令用临时的；
#    再加一行 YUNNAN_ASSET_ROOT=<资产目录>（演练栈的项目目录是别的工作树，那里没有权重）
#    生成演练用的 config.yaml（GeoView 浏览器端直连后端的地址是构建时从 config.yaml 写进产物的，
#    不换端口，演练页面会去连生产的 5008）：
python deploy/release_tool.py rehearsal-config <发布目录> <演练 config.yaml>
# 2) 起容器之前先审查隔离性：临时钉住 → 渲染并逐项断言（容器名、端口、卷、网络、挂载）→ 解除钉住
#    （一次性脚本在交接目录 scripts/rehearsal_isolation_check.py）
# 3) 首次上线：
deploy/switch_release.sh <发布目录> --project yunnan-rehearsal \
  --file docker-compose.prod.yml --file deploy/rehearsal/compose.rehearsal.yml \
  --env-file <演练环境文件> --env-file image_bundle.env \
  --config-override <演练 config.yaml> --with-mysql --skip inference-worker \
  --backend-url http://127.0.0.1:25008 --frontend-url http://127.0.0.1:23000 \
  --miner-api-url http://127.0.0.1:28000 --miner-web-url http://127.0.0.1:24000
# 4) 回滚演练：deploy/switch_release.sh --rollback <同样的选项>
# 5) 清理：先 down（不带 -v），再按名字逐个删带演练前缀的卷；最后删演练环境文件（里面有临时口令）
```

演练前后各给生产与验收两套栈的容器拍一次快照（容器 ID、启动时间、重启次数、挂载），比对必须完全相同。

演练库必须是新的、演练存储必须是空的：两者要对得上。新库配旧存储时，后端启动脚本给种子项目做空间迁移，
发现目录已存在会崩一次（下次启动换了自增编号才起来）。

## 6. 演练结果

### 第一轮（2026-11-25 上半，候选 `b2b892e`）

## 7. 上线或回滚时还开着的旧页面

两个站点的路由页面是按需加载的代码块（GeoView：`/js/<编号>.<哈希>.js`，Miner：`/assets/<名字>-<哈希>.js`），
文件名带内容哈希，发一次版本就换一批。上线或回滚之后，还开着旧页面的浏览器切到没打开过的页面时，会来要旧名字的代码块。

- **此前**：静态服务对不存在的文件一律回落成 `index.html`，浏览器把一段 HTML 当脚本执行，报
  `SyntaxError` / `ChunkLoadError`，页面停在原处，没有任何提示（真实浏览器里复现过）。
- **现在**（`docker/static-server.mjs`）：对缺失的代码块回一小段脚本，弹出"系统已更新到新版本，需要刷新页面后才能继续使用"。
  点确定立即刷新到新版本（尚未保存的内容会丢失；刷新后落在当前页面，要重新打开要去的页面）；点取消留在本页，可以先保存再手动刷新。
  同一标签页 30 秒内只问一次，刷新之后要的还是不存在的代码块（构建本身有问题）也不会反复弹。其它缺失文件照旧回落成首页。
- **管不到的**：已经停在旧编辑器里的页面（代码已在内存里）不会收到提示；它们可以继续保存，但简化走的是旧逻辑。
  回滚到 `820dd50` 后，静态服务也是那一版的老代码，没有这个提示，旧的新页面会像"此前"那样失败，需要用户手动刷新。

行为测试：`node --test docker/static-server.test.mjs`（真实起一个服务进程，8 项）。

## 8. 运行时资产移出开发树：最小可行方案（只出方案，没有移动任何文件）

**现状。** 7 项运行时资产共 9.46 GiB，全在被 `.gitignore` 忽略的目录里，Git 只跟踪一个配置文件
`backend/model/mmseg_config/dinov3_swinV1.py`。它们留在开发主树里有三个问题：主树里的权重被人替换，线上下一次重启就
用上，发布目录只记账、不隔离；换一台机器部署会丢；线上到底用哪一版权重，此前没有记录。

**事实（决定了方案怎么做）。**

- 容器里的路径由代码写死（`/app/backend/model/...`），宿主机上放在哪里只取决于 compose 的 `YUNNAN_ASSET_ROOT`。迁移不需要改代码。
- 现在有三个使用者：生产（靠"整个 `backend` 目录挂进去"带进来）、演练栈（经 `YUNNAN_ASSET_ROOT`）、
  验收栈（`yunnan-acc-b2-inference-worker` 直接挂开发主树的 `mmseg_config` 目录）。所以**只能"复制 + 改指向"，不能"移动"**。
- 推理镜像构建时从构建上下文（开发树）拷 `dinov3_swinV1/{mmseg,dinov3}` 的源码，构建脚本默认也从开发树读推理权重做校验；
  源码挪走之后、重建镜像之前要先改构建脚本。
- 资产目录里有杂物：2,995 个下载标记文件（共 0.2 MiB）、3 个 wheel 安装包（114 MiB）、1 个配置里没有引用的预训练权重（110 MiB）。

**方案。**

1. **位置**：`D:/yunnan-assets/runtime/<资产集编号>/backend/model/...`——数据盘上、仓库与发布目录之外的独立目录，按内容版本化。
   编号取这 7 项资产指纹的组合摘要前 12 位；旁边放 `SHA256SUMS.json`（就是 `RELEASE.json` 的 `assets` 段）和一份说明。
2. **步骤**（改挂载就要重启容器，放进维护窗口或单独安排）：
   1. **复制**，不删源。第一次原样复制（包括那些标记文件），保证与现有清单逐字节一致。
   2. **核对**：`python deploy/release_tool.py check <候选发布目录> --asset-root D:/yunnan-assets/runtime/<编号>` 通过。
   3. 在生产 `.env` 里加 `YUNNAN_ASSET_ROOT=D:/yunnan-assets/runtime/<编号>`。写进 `.env` 而不是只靠命令行环境变量：
      之后任何人按旧习惯 `up -d`，用的也是同一份。
   4. 下一次切换（或单独重启挂了资产的三个容器）之后，`deploy/verify_release.sh <候选> --hash-assets`：容器内 SHA256 与清单一致。
   5. 验收栈的 compose 改指向新位置（或者退役），重启验证。
   6. 以上都稳定之后，再删开发树里的那 9.5 GB。
3. **磁盘**：过渡期两份并存，D 盘要多占 9.5 GB（现在剩约 45 GB，够）。
4. **风险与注意**：
   - 两份并存期间容易看错"线上用的是哪一份"：以 `.env` 里的 `YUNNAN_ASSET_ROOT` 和 `verify --hash-assets` 为准。
   - 不要用目录联接（junction）代替复制：此前出过 `git worktree remove` 穿透联接、删空主树依赖目录的事故。
   - 开发树里本地跑需要权重的测试时，要自己设 `YUNNAN_ASSET_ROOT`；后端测试套件不加载权重，不受影响。
   - 资产指纹缓存按路径记键，新位置第一次要重算 10 GB。
   - 清理标记文件会改变目录指纹，需要重新生成清单，并在真 GPU 上重新验收推理——另案处理，不与迁移混在一起。
5. **不做的**：不把权重加进 Git；不改容器内路径；不改推理镜像。

## 9. 已知限制与没测的

- 演练栈不带推理 worker（要 GPU 和 4.5 GiB 内存）。本轮对推理环境只做了不占 GPU 的静态核对：镜像内容契约，以及按 compose
  渲染结果起一次性容器、把 worker 的启动过程走到加载模型之前（依赖、GDAL / PROJ、自检脚本、应用上下文、配置解析与类型注册、
  权重结构、容器内资产 SHA256），16 步全过。**没有真的跑过推理**，模型加载、GPU 推理、矢量化、发布要在维护窗口里做强制验收。
- 顺带查出的既有问题（与发布隔离无关，没有改）：后端容器里的旧同步推理接口（`POST /api/analysis/semantic_segmentation`，
  GeoView 的图片上传语义分割走它）起子进程用 `/opt/conda/envs/MMSeg310` 加载模型，而那个环境里是 CPU 版 torch 2.2.2 加
  mmcv 2.2.0，随附的 mmseg 1.1.2 要求 mmcv < 2.2.0，导入即断言失败。推理 worker 不走这条链（它在进程内、用 `/opt/venv` 加载）。
- 发布目录里的 `config.yaml` 是提交里的那一份。换到另一台地址不同的服务器时，GeoView 浏览器端直连后端的地址
  需要另一份 `config.yaml`——现在只能在 compose 里额外覆盖，没有专门的入口。
- 运行时资产默认仍在开发主树里（见第 8 节的迁出方案）。
- 不设置 `YUNNAN_ASSET_ROOT` 的机器上如果没有权重，compose 会把挂载源建成空目录或空文件（Docker 的默认行为），
  与改造前"没有权重"的状态等价，但会留下一个 0 字节的 `model.pth`，容易看错。
- 本机 Docker 虚拟机只有 4 核、6 GB，演练与生产、验收栈同在一台机器上；GeoView 构建期间生产会变慢。
- 在这台机器之外的环境（Linux 宿主、别的 Docker 配置）没有测过。
